## 一、核心知识体系（无教材也成立的骨架）

### 1. 关系模型三要素
关系数据库 = 用集合论处理数据的二维表系统。三要素：数据结构（表）+ 数据操作（关系代数）+ 完整性规则。

### 2. 关系术语速查
| 术语 | 含义 | SQL 对应 |
|------|------|---------|
| 关系 | 一张表 | table |
| 元组 | 一行 | row |
| 属性 | 一列 | column |
| 域 | 取值范围（必须原子） | type |
| 候选码 | 唯一标识一行的属性组（可多个） | UNIQUE |
| 主码 | 候选码里选 1 个 | PRIMARY KEY |
| 主属性 | 在**任一**候选码里的属性 | — |
| 外码 | 不是本表码、但是别表码 | FOREIGN KEY |
| 全码 | 所有属性合起来才是码 | — |

### 3. 完整性 3 类
| 类型 | 规则 | SQL |
|------|------|-----|
| 实体完整性 | 主码唯一且非空 | PRIMARY KEY |
| 参照完整性 | 外码取空 **或** = 被参照主码值（防悬空引用） | FOREIGN KEY |
| 用户定义完整性 | 业务语义约束 | CHECK / NOT NULL |

### 4. 关系运算（符号 ↔ SQL）
- 选择 σ = `WHERE`（选行）
- 投影 π = `SELECT 列`（选列）
- 连接 ⋈ = `JOIN`（θ/等值/自然；**自然连接去重复列**）
- 并∪ 差− 交∩ 笛卡尔积× = 集合运算
- 除 ÷ = "找包含所有目标的"

### 5. 函数依赖（有方向、单向）
- X→Y：X 决定 Y（X 同则 Y 必同），反向不一定成立
- **完全依赖**：X→Y 且 X 的任何真子集不能决定 Y
- **部分依赖**：不完全（某真子集也能决定 Y）← **只在复合码时出现**
- **传递依赖**：X→Y→Z（**单表内**）

### 6. 范式（1NF ⊂ 2NF ⊂ 3NF ⊂ BCNF ⊂ 4NF）
| 范式 | 消除什么 | 口诀 |
|------|---------|------|
| 1NF | —（分量原子） | 不可再分 |
| 2NF | 非主属性对码的**部分**依赖 | 治部分依赖 |
| 3NF | 非主属性对码的**传递**依赖 | 治传递依赖 |
| BCNF | **主属性**对码的部分/传递依赖 | 管主属性 |

> 关键：**单属性主码天然 2NF**（无部分依赖）。只考虑函数依赖→最高 BCNF；考虑多值依赖→最高 4NF。

### 7. 数据库设计 6 阶段
需求分析 → 概念设计（E-R 图）→ 逻辑设计（E-R 转关系模式）→ 物理设计（索引/存储）→ 实施 → 运维

### 8. E-R 图转关系模式（高频考点）
| 联系 | 转换 |
|------|------|
| 1:1 | 归并到任一方 |
| 1:n | 归并到**多方** |
| **m:n** | **必须独立成表**（码 = 两方码组成） |

### 9. 反规范化
规范化后，为查询性能**有选择加冗余**（冗余列/派生列/表分割）。代价：冗余 → 不一致 → 需数据同步（应用同步/批量同步/触发器同步）。反规范化 ≠ 从未规范化。

## 二、顾问指引（真实项目里 AI 怎么用这些知识）

当用户做数据库设计 / 问表结构时，按此引导：

1. **先理实体和联系**：有哪些实体？实体间是 1:1 / 1:n / m:n 哪种？
2. **E-R 转表**：m:n 提醒**必须独立建关联表**（如 user-product 的订单/购物车表）。
3. **查范式**：复合码表查部分依赖；任何表查传递依赖 → 不合规就拆表。
4. **物理设计**：高频查询字段建索引；**读多写少**的表才适合多索引（写多索引维护代价高）。
5. **反规范化**：只在"规范化后查询慢"时考虑，且必须说明同步代价。

## 三、常见误区（AI 自检红线，来自真实学习错题）

- ❌ **单主码表说"部分依赖"** → 单主码无部分依赖，其问题是传递依赖（3NF）
- ❌ **把多表间外码关联当"传递依赖"** → 传递依赖是**单表内** X→Y→Z；表间外码是引用，不是函数依赖
- ❌ **主属性 = 候选码交集** → 应为"属于**任一**候选码"
- ❌ **等值连接 = 自然连接** → 自然连接去掉重复列
- ❌ **反规范化 = 从未规范化** → 反规范化是先规范化好、再为性能加冗余
- ❌ **演示部分依赖用单主码例子** → 必须用复合码主码的表

## 四、AI 给建议前的自检清单

- 这张表主码是单属性还是复合？→ 决定有无部分依赖可能
- 这个依赖是单表内还是跨表？→ 跨表不是函数依赖
- 联系是 1:1 / 1:n / m:n 哪种？→ 决定转关系模式的方式
- 建索引的字段读多还是写多？→ 写多不宜建索引
- 我的建议能溯源到上面哪条知识？→ 不能溯源的建议要标注"工程经验，非教材"
