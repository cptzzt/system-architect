## 一、核心知识体系

### 1. 架构风格是什么

软件架构风格 = 描述某一特定应用领域中**系统组织方式**的**惯用模式**。
- 它定义一个**系统家族**：一个**词汇表**（构件 + 连接件类型）+ 一组**约束**（如何组合）。
- 反映领域众多系统共有的**结构和语义特性**，指导模块/子系统如何组织成完整系统。
- 核心目标：**体系结构级的软件重用**（不同系统用同一体系结构）。
- 例子：说"客户/服务器"，不必给细节，听者立刻明白组织方式。

### 2. 五大类风格总览（高频考点）

| 大类 | 子风格 | 基本构件 | 连接件 | 核心特征 |
|------|--------|---------|--------|---------|
| **数据流** | 批处理 / 管道-过滤器 | 应用程序 / 过滤器 | 数据载体 / 管道 | 数据驱动执行顺序 |
| **调用/返回** | 主程序-子程序 / 面向对象 / 层次 / C/S | 模块、对象、层、客户端 | 过程调用 | 分而治之，控制流驱动 |
| **以数据为中心** | 仓库 / 黑板 | 中央数据 + 独立构件 / 知识源 | 仓库交互 / 黑板访问 | 围绕共享数据 |
| **虚拟机** | 解释器 / 规则系统 | 解释引擎+被解释代码 / 规则+解释器 | — | 人造运行环境，解析自定义语言 |
| **独立构件** | 进程通信 / 事件系统 | 独立进程 / 模块 | 消息传递 / 事件广播 | 构件不直接通信，松耦合 |

> 💡 **5 大类脊柱**：按**构件联系方式**分（数据怎么流 / 怎么调 / 围什么转 / 怎么解析 / 怎么通知）。每类 2 子风格（调用返回 4 个），多为"对立两极"（如数据流的整批 vs 连续）。
>
> ⚠️ **专家系统横跨解释器 + 规则系统**：教材把专家系统归为**解释器**典型例子（推理引擎=解释器），但核心机制是**规则系统**（if-then 知识库）。考试问"专家系统属哪种风格"按教材答**解释器**；规则系统 4 组成（规则集 + 解释器 + 选择器 + **工作内存**）也常考。

### 3. 数据流体系结构风格

**特点**：无概念上的程序计数器；指令执行性仅由**输入参数可用性**决定，执行顺序不可预测（行为不确定）。

#### 3.1 批处理
- 构件 = 独立应用程序；连接件 = 某种数据媒介（如磁带），定义数据流拓扑。
- **关键约束**：每步必须等前一步结束才开始；**数据必须完整**，整体传递。
- 类比：传统 ETL 作业、夜间数据批处理。

#### 3.2 管道-过滤器（Pipe-Filter）
- 构件 = 过滤器（Filter），有输入和输出；连接件 = 管道（Pipe）传输数据流。
- 一个过滤器的输出是下一个的输入，序贯处理。
- 类比：Unix 管道 `cmd1 | cmd2 | cmd3`、流式数据处理、编译器的词法→语法→语义→代码生成各阶段。
- 与批处理区别：数据**源源不断**流式传递，而非整体等待。

### 4. 调用/返回体系结构风格

**核心思想**：分而治之——把复杂大系统分解为子系统，降低复杂度、增加可修改性。程序从入口执行，结束返回控制给调用者。

#### 4.1 主程序/子程序
- 单线程控制；构件 = 主程序 + 子程序（可合成模块）；连接件 = 过程调用。
- 调用关系**层次性**；子程序正确性依赖其调用的子程序正确性。

#### 4.2 面向对象（OO）
- 基于数据抽象和 OO；构件 = 对象（抽象数据类型的实例）；数据表示和操作**封装**在一起。
- 类比：Java/C# 的类与对象系统。

#### 4.3 层次型（Layered）
- 每层为上层服务、作为下层客户；构件在各层实现虚拟机。
- 连接件 = 层间交互协议；拓扑约束 = **相邻层**间交互约束。
- **优点**：每层最多影响两层；相邻层接口不变即可换实现 → 强复用支持。
- 类比：OSI 七层、TCP/IP、操作系统内核层、三层架构（表示/业务/数据）、Spring 分层。

#### 4.4 客户端/服务器（C/S）
- 基于资源不对等、为共享而设计。
- **两层 C/S**：数据库服务器 + 客户应用程序 + 网络；后台管数据，前台做交互 → **"胖客户机，瘦服务器"**。
- **三层 C/S**：增加**应用服务器**，应用逻辑驻留其上，客户机仅表示层 → **"瘦客户机"**。
  - 三层：表示层（GUI）/ 功能层（业务逻辑）/ 数据层（DBMS），逻辑独立。
- 类比：B/S 是三层 C/S 的演化（浏览器作表示层）；微服务架构是 C/S 在服务间的细化。

### 5. 以数据为中心的体系结构风格

#### 5.1 仓库（Repository）
- 仓库 = 存储和维护数据的中心场所。
- 两类构件：① 中央数据结构（说明当前数据状态）② 一组独立构件（对中央数据操作）。
- 连接件 = 仓库与独立构件间的交互（交互方式变化大）。
- 类比：数据库中心架构、IDE 的中央代码库、企业数据仓库。

#### 5.2 黑板（Blackboard）
- 适用于**复杂的非结构化问题**，综合运用多种知识源。
- 三要素：**黑板**（共享数据结构，解空间组织成分级结构）+ **知识源**（独立知识模块，转换层次信息）+ **控制**。
- 传统应用：信号处理（语音识别、模式识别）；其他：松耦合代理数据共享。
- 与仓库区别：黑板强调**分级结构 + 多知识源协同求解**，仓库更偏单纯数据共享。

### 6. 虚拟机体系结构风格

**核心思想**：人为构建运行环境，在其上解析/运行自定义语言，增加架构灵活性。

#### 6.1 解释器
- 组成：解释引擎 + 被解释代码存储区 + 当前工作状态数据结构 + 源代码执行进度数据结构。
- 含虚拟机，仿真硬件执行过程；弥合**程序语义与硬件语义**差异。
- **缺点**：执行效率较低。
- 典型例子：专家系统、JVM、脚本语言解释器。

#### 6.2 规则系统
- 组成：**规则集 + 规则解释器 + 规则/数据选择器 + 工作内存**。
- 类比：业务规则引擎（Drools 等）、产生式专家系统。

### 7. 独立构件体系结构风格

**核心思想**：每个构件相对独立，**不直接通信**，降低耦合、提升灵活性。

#### 7.1 进程通信
- 构件 = 独立的过程（命名过程）；连接件 = **消息传递**。
- 消息方式：点到点、同步/异步、远程过程调用（RPC）。
- 类比：微服务间消息队列通信、Actor 模型。

#### 7.2 事件系统（基于事件的隐式调用）
- 构件不直接调用过程，而是**触发/广播事件**；其他构件在事件中注册，事件触发时系统自动调用注册的过程。
- **关键特征**：事件触发者**不知道**哪些构件会被影响——不能假定处理顺序，甚至不知哪些过程被调用。
- 因此常作为**显式调用的补充**形式存在。
- 应用：IDE 工具集成、DBMS 数据一致性约束、UI 系统数据管理、编辑器语法检查。
- 类比：发布-订阅（Pub-Sub）、观察者模式、消息总线、ESB、React 事件机制、Spring 事件。

## 二、顾问指引（真实项目 AI 怎么用）

- 用户问"该选什么架构风格"：先看**数据流向**（流式→管道过滤器）、**共享数据**程度（强共享→仓库/黑板）、**耦合要求**（松耦合→独立构件/事件）、**是否需灵活解析**（→虚拟机）。
- 用户做企业应用：默认推荐**层次型 / 三层 C/S**，业务复杂再叠加面向对象。
- 用户做数据密集批处理：**批处理**（整体）vs **管道-过滤器**（流式）按数据是否流式选。
- 用户做需要规则可配置的系统（风控、计费）：**规则系统**风格，规则与执行分离。
- 用户做高并发解耦系统：**事件系统 / 进程通信**，强调触发者与处理者解耦。
- 用户做遗留系统集成：注意**体系结构失配**（构件/连接子/全局假设三方面冲突）。

## 三、常见误区（AI 自检红线）

- ❌ **把"架构风格"等同于"设计模式"**：架构风格是**体系结构级**的复用（系统家族），设计模式是更细粒度的局部方案。
- ❌ **混淆批处理与管道-过滤器**：批处理**数据完整、整体传递、步骤串行等待**；管道-过滤器**数据流式、源源不断**。
- ❌ **两层 C/S 和三层 C/S 的胖瘦说反**：两层 = **胖客户机瘦服务器**；三层 = **瘦客户机**（加了应用服务器）。
- ❌ **以为层次型可跨层任意调用**：层次型约束是**相邻层间**交互，每层最多影响上下两层。
- ❌ **把仓库和黑板混为一谈**：仓库是中央数据 + 独立构件操作；黑板强调**分级解空间 + 多知识源协同**，专门用于复杂非结构化问题。
- ❌ **以为事件系统触发者知道处理者**：事件系统核心就是**触发者不知影响谁**，处理顺序也不可假定——这是它与显式调用的本质区别。
- ❌ **解释器说成"性能好"**：解释器/虚拟机风格**执行效率较低**，是用性能换灵活性。
- ❌ **遗漏 5 大类的归属**：5 大类 = 数据流 / 调用-返回 / 以数据为中心 / 虚拟机 / 独立构件，子风格归属不能错位（如把"黑板"归到虚拟机）。
