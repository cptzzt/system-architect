## 一、核心知识体系

### 1. 软件架构（SA）是什么

- **定义核心**：SA 是系统的一个或多个**结构**，包含**构件**（Component）、构件的**外部可见属性**、以及构件间的**相互关系**。
- **关键认知**：SA **不是可运行软件**，而是一种**表达/蓝图**，让工程师能够：
  1. 分析设计在满足需求上的有效性
  2. 在设计变更成本较低的阶段权衡方案
  3. 降低构造风险
- **构件粒度**：小到模块/面向对象的类，大到数据库、中间件、客户-服务器网络配置。
- **术语统一**：「体系结构」=「架构」，本书同义（Software Architecture, SA）。

### 2. SA 设计的两个层次（设计金字塔）
| 层次 | 关注 |
|------|------|
| 数据设计 | 传统系统的数据构件、OO 系统中类的定义（封装属性+操作） |
| 体系结构设计 | 软件构件的**结构、属性、交互作用** |

### 3. SA 与生命周期各阶段（SA 贯穿全生命周期）

| 阶段 | SA 的角色 / 关键活动 |
|------|---------------------|
| 需求分析 | 需求模型（问题空间）→ SA 模型（解空间），关注**可追踪性**；已有 SA 可反哺新系统需求工程 |
| 设计 | SA 研究最早最多：模型描述、设计与分析、经验复用（**3 层描述**见下） |
| 实现 | 项目组织、配置管理、SA→实现过渡（语言元素引入 / 模型精化 / 构件组装）、基于 SA 的测试 |
| 构件组装 | SA 作蓝图；**体系结构失配**问题（见误区） |
| 部署 | 提供高层部署视图；分析部署方案质量属性（性能、可靠性） |
| 后开发 | **动态 SA**（运行时变化）、**SA 恢复与重建**（4 类方法） |

**设计阶段 SA 模型描述的 3 层次**：
1. 基本概念（构件 + 连接子 Connector，连接子是与构件同级、独立的互联实体）
2. **ADL**（Architecture Description Language，体系结构描述语言）—— 重视连接子是 ADL 区别于其他建模语言的特征
3. **多视图表示**（关注点分离）

**典型多视图方案**：
- **4+1 模型**：逻辑 / 进程 / 开发 / 物理 + 场景（统一）
- Hofmeister 4 视图：概念 / 模块 / 执行 / 代码
- CMU-SEI Views and Beyond：模块视图 / 构件连接子视图 / 分配视图
- 工业标准：IEEE 1471-2000、RM-ODP、UML、Zachman

> ⚠️ **两套 4+1 别混（高频陷阱，都教材原文）**：
> - **架构 4+1**（教材 7.1.2）：逻辑 / 过程 / 开发 / 物理 + **场景**（"+1"=场景）
> - **RUP/UML 4+1**（教材 2.6 + 5.1）：用例 / 逻辑 / 实现 / 进程 / 部署（"+1"=用例视图，带人员对应：用例=分析/测试、逻辑=最终用户、实现=程序员、进程=系统集成、部署=系统工程师）
> - 近义干扰：开发≈实现、物理≈部署≈配置、过程≈进程；考试出现近义选项时**先判题目考哪套，再选教材精确匹配项**。

### 4. 动态 SA 的两类变化
| 类型 | 来源 | 例子 |
|------|------|------|
| 内部执行导致 | 软件内部触发 | 服务器收到请求时创建新构件、自适应系统切换连接子 |
| 外部重配置 | 系统外部请求 | 高安全系统不停机升级、操作系统热升级 |

**动态 SA 研究两部分**：① 设计阶段支持（变化的描述、修改策略、影响分析）② 运行时刻基础设施（SA 维护、约束保证、变化映射）。

### 5. SA 重建（Architecture Recovery）4 类方法
1. 手工重建
2. 工具支持的手工重建（如 KLOCwork inSight 从源码取构件视图）
3. 查询语言自动聚集（源码→数据库→查询得到 SA 视）
4. 其他技术（数据挖掘等）

### 6. SA 的重要性（8 点，常考列举）
1. **满足系统品质**：功能性靠构件交互支持，品质（性能/安全/可维护性）靠架构实现
2. **受益人达成共识**：文档化的架构让涉众辩论、权衡、达成一致
3. **支持计划编制**：依赖关系 → 工作分配、成本估算、风险管理
4. **指导系统开发**：为设计/实现人员提供可靠框架，定义接口标准
5. **管理复杂性**：构件抽象 + 递归分解（大问题拆小问题）
6. **为复用奠基**：支持大粒度资源复用（现成构件、遗留系统）
7. **降低维护费用**：维护人员作为首要涉众，预留适应性/扩充性
8. **支持冲突分析**：改变前推断影响（组件依赖、需求追溯）

### 7. ABSD（基于架构的软件开发）方法

**ABSD = Architecture-Based Software Design**，由体系结构驱动 = 商业 + 质量 + 功能需求的组合驱动。

**3 个基础**：
1. **功能分解**（用已有的内聚/耦合技术）
2. **选择体系结构风格**实现质量和商业需求
3. **软件模板**的使用

**核心特点**：递归 + 迭代；**设计活动可从总体功能框架明确就开始**（需求未必完整），需求抽取与设计**并行**——适合产品线/长期运行系统。

**3 个设计元素**（自顶向下递归细化）：系统 → 概念子系统 + 软件模板 → 概念构件 + 附加模板 → 实际构件 / 类。

**视角与视图**：静态视角判断质量特性、动态视角判断行为特性；常用逻辑 / 进程 / 实现 / 配置视图。

**用例 + 质量场景**：
- 用例捕获**功能需求**
- 质量场景捕获**质量需求**：变更场景 / 性能场景 / 可靠性场景 / 交互性场景
- 质量场景必须含**预期**和**非预期**（非预期定边界条件）

### 8. ABSD 开发模型 6 子过程

```
体系结构需求 → 设计 → 文档化 → 复审 → 实现 → 演化
                                  ↑__________________|  (演化可回到需求或文档化)
```

| 子过程 | 关键产出 / 活动 |
|--------|----------------|
| **需求** | 需求来自 3 方面：质量目标 / 商业目标 / 开发人员商业目标；需求获取 → 标识构件（生成类图→类分组→打包成构件）→ 需求评审 |
| **设计** | 提出架构模型（选风格）→ 映射构件 → 分析构件交互 → 产生架构 → **设计评审（外部人员）** |
| **文档化** | 输出 2 文档：**体系结构规格说明** + **质量设计说明书**；文档要从使用者角度、分发到所有开发人员、保持最新 |
| **复审** | 外部人员（用户代表+领域专家）参加；常搭建**可运行最小化系统**评估技术和协作风险 |
| **实现** | 以文档化架构说明书为基础 → 构件库查找/开发 → 组装 → 测试（单构件 + 整体） |
| **演化** | 需求变化归类 → 演化计划 → 修改/增删构件 → 更新交互 → 组装测试 → 技术评审 |

## 二、顾问指引（真实项目 AI 怎么用）

- 用户问"要不要先做完需求再设计架构"：讲清 ABSD 的并行性——总体框架明确即可开始设计，需求与设计并行，特别适合需求难全预先决定的产品线/长期系统。
- 用户问"架构文档要写什么"：对照"两文档"——规格说明（结构 + 接口约束）+ 质量设计说明书，强调分发与时效性。
- 用户问"为什么要做架构评审/最小化系统"：讲清风险前置——架构设计阶段变更成本低，复审和原型能在编码前暴露技术与协作风险。
- 用户在迭代演化时：用演化 6 步引导，强调"需求变化归类"先于"改架构"，避免无序变更。
- 用户做需求→架构映射：用 ABSD 的"类图→类分组→打包成构件"路径，强调类的分组标准（隔离类、概括关联类、聚合关联类各成一组）。

## 三、常见误区（AI 自检红线）

- ❌ **把 SA 当成可运行软件**：SA 是蓝图/表达，不是程序本身，作用是分析、权衡、降风险。
- ❌ **以为 SA 只在设计阶段有用**：SA 贯穿全生命周期（需求/设计/实现/组装/部署/后开发都涉及）。
- ❌ **混淆构件与连接子**：连接子是与构件**同等级别**的独立实体（早期只是模块互联机制，后独立出来）；ADL 的特征就是**重视连接子**。
- ❌ **把体系结构失配只归到构件本身**：失配来自 3 方面——① 构件（基础设施/控制模型/数据模型假设冲突）② 连接子（交互协议/数据模型假设冲突）③ 全局体系结构假设冲突。
- ❌ **ABSD 设计开始 = 需求结束**：ABSD 设计可与需求抽取**并行**，设计开始不终止需求活动。
- ❌ **质量场景只列好情况**：必须含**预期 + 非预期**场景（如用户增 10% 是预期，增 100% 是非预期），非预期定边界。
- ❌ **架构评审用内部人员**：设计评审和复审都强调**外部独立人员**参与（用户代表、领域专家）。
- ❌ **演化直接改构件**：演化第 1 步是**需求变化归类**（对应到已有构件或标记新构件），再订计划，不能跳过。
