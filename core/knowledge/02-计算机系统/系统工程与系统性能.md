## 一、核心知识体系

### Part A：系统工程

#### A1. 定义与核心思想
**系统工程（Systems Engineering, SE）**= 一种**跨学科的组织管理技术**，不是某门具体工程学科，而是一套方法论。
- 核心思想：**从整体出发，追求全局最优**（而非局部最优）
- 系统（ISO/IEC 15288:2008）：人造的、由交互元素组织起来以实现特定目的的组合。系统元素包括硬件、软件、数据、人员、流程、设施、材料等
- **系统之系统（SoS, System of Systems）**：系统元素本身也是系统（如 GPS 既是航空系统子系统，也是汽车导航子系统）

> 注意：系统工程里的"系统"与"操作系统"的"系统"完全不同——前者是组织管理方法论，后者是具体软件。

#### A2. 五种系统工程方法（高频对比）

| 方法 | 提出者 | 核心思想 | 适用 |
|------|--------|---------|------|
| **霍尔三维结构** | Hall 1969 | **最优化**（硬系统方法论 HSM） | 需求明确、可量化的工程问题（如阿波罗登月） |
| **切克兰德方法** | Checkland | **比较与探寻**（软系统方法论） | 需求不清晰、难以量化的社会/经济/管理问题 |
| **并行工程** | — | 各部门从设计开始**同时参与**整个生命周期 | 替代串行开发，避免后期返工 |
| **综合集成法** | 钱学森 1990 | 处理**开放的复杂巨系统** | 社会系统、经济系统 |
| **WSR 方法** | 顾基发 1994 | **物理-事理-人理**，"懂物理、明事理、通人理" | 综合考虑物/事/人的方法论 |

**霍尔三维结构的三维**：
- 时间维（7 阶段）：规划→拟订方案→研制→生产→安装→运行→更新
- 逻辑维（7 步骤）：明确问题→确定目标→系统综合→系统分析→优化→决策→实施
- 知识维：各种专业知识

**切克兰德 7 步骤**：认识问题 → 根底定义 → 建立概念模型 → 比较及探寻 → 选择 → 设计与实施 → 评估与反馈

**并行工程 vs 串行**：
- 串行：设计→工艺→制造→测试（逐步来，后期发现问题回头改成本高）
- 并行：设计+工艺+制造+测试**同时参与**（早期发现问题，避免大量返工）

**综合集成法的系统分类**：简单系统 → 巨系统 → 简单巨系统 → 复杂巨系统 → **开放的复杂巨系统**（与环境有物质/能量/信息交换）
特点：定性定量结合、理论经验结合、多学科综合、必须有大型计算机系统支持

**WSR**：
- 物理（Wuli）：客观存在的物质运动规律（自然科学方法）
- 事理（Shili）：做事的道理（运筹学、管理科学、系统工程方法）
- 人理（Renli）：做人的道理（关系、感情、利益、协调）
- 实践准则："懂物理、明事理、通人理"

#### A3. 系统工程生命周期七阶段
探索性研究 → 概念 → 开发 → 生产 → 使用 → 保障 → 退役

#### A4. 四种生命周期方法
| 方法 | 核心思想 | 适用场景 |
|------|---------|---------|
| 计划驱动 | 遵守规定流程，关注文档完整性和需求可追溯性 | 大型团队、多公司协作 |
| 渐进迭代式开发 (IID) | 初始能力 → 连续交付 → 逐步完善 | 需求不清晰、需引入新技术 |
| 精益开发 | 消除浪费，向客户交付最大价值 | 源自丰田生产方式 |
| 敏捷开发 | 迭代开发，欢迎需求变更，快速交付 | 软件开发 |

#### A5. MBSE（基于模型的系统工程）
用建模方法支持系统从需求到设计到验证的全生命周期。
**三大支柱**：建模语言（SysML，基于 UML 扩展）+ 建模工具 + 建模思路

### Part B：系统性能

#### B1. 各类设备的性能指标
| 设备 | 关键性能指标 |
|------|------------|
| 计算机 | 主频、运算速度、内存容量、存取周期、吞吐率、响应时间、**RASIS 特性** |
| 路由器 | 设备吞吐量、端口吞吐量、丢包率、时延、时延抖动 |
| 交换机 | 背板吞吐量、缓冲区大小、最大 MAC 地址表、支持 VLAN 数 |
| 操作系统 | 上下文切换、响应时间、吞吐率、资源利用率 |
| 数据库 | 最大并发事务数、最大连接数、负载均衡能力 |
| **Web 服务器** | **最大并发连接数、响应延迟、吞吐量**（三大核心） |

#### B2. RASIS 特性（计算机综合评价指标）
- **R**eliability 可靠性
- **A**vailability 可用性
- **S**erviceability 可维护性
- **I**ntegrity 完整性
- **S**ecurity 安全性

#### B3. 性能计算方法
主要方法：定义法、公式法、程序检测法、仪器检测法。
常用计算：MIPS（Millions of Instructions Per Second，每秒百万条指令）、峰值计算、等效指令速度（吉普森/Gibson 法）。

#### B4. 性能调整（三步准备 + 循环过程）
**调整前必须做三件准备**：
1. **识别约束**——找到瓶颈在哪（CPU/内存/磁盘 I/O/网络？），不能瞎优化
2. **指定负载**——定义"正常使用"是什么样的（如 100 并发用户）。**定义输入压力**
3. **设置性能目标**——定义"达标"标准（如响应时间 < 200ms）。**定义输出要求**

> 负载和目标是一对：负载是"考什么题"，目标是"考多少分算及格"。**缺一不可**——没有负载的指标没意义，没有指标的负载也没意义。

**调整是循环过程**：收集 → 分析 → 配置 → 测试，反复进行。

#### B5. 阿姆达尔定律（Amdahl's Law，⭐ 高频计算题）
**核心思想**：系统性能提升程度，取决于**被改进部分在总执行时间中占的比例**。

**公式**：
```
总加速比 = 1 / ((1 - 增强比例) + 增强比例 / 增强加速比)
```
- **增强比例**：可改进部分占原总执行时间的比例（≤ 1）
- **增强加速比**：改进部分自身的速度提升倍数

**例子**：某程序 60% 时间在做计算（可加速），换快 3 倍的 CPU。
```
总加速比 = 1 / ((1 - 0.6) + 0.6 / 3) = 1 / (0.4 + 0.2) = 1 / 0.6 ≈ 1.67 倍
```
→ 整体只快 1.67 倍，**不是 3 倍**。

**关键结论**：
- 增强比例 = 1（全部可加速）时，总加速比 = 增强加速比（理想情况）
- 现实中总有不可加速部分，**总加速比永远小于增强加速比**
- 不可加速的部分 = **瓶颈**
- **优化占比高的部分收益最大**——性能不达标先优化占比最高的部分

#### B6. 基准测试程序（准确度从高到低）
1. **真实的程序**——实际应用程序（如用真实业务跑大负载）
2. **核心程序**——从真实程序中提取最频繁使用的部分
3. **小型基准程序**——简化的测试程序
4. **合成基准程序**——人工编写，混合各种操作模拟真实负载（不做任何实际有用的工作）

> 常见基准：Dhrystone（整数）、Linpack（浮点）、Whetstone（浮点整数综合）、SPEC（综合）、TPC（数据库事务）。
> 基准测试程序是测**硬件/系统**的——像考试题考学生，不是考出题人。

#### B7. Web 服务器性能评估
三个核心指标：最大并发连接数、响应延迟、吞吐量。
三种评测方法：基准性能测试、压力测试、可靠性测试。

#### B8. 系统监视三种方式
1. **系统命令**：Linux 的 `w`、`ps`、`last`；Windows 的 `netstat`
2. **系统日志**：查阅特定时间的运行状态
3. **可视化工具**：Windows 的 Perfmon

## 二、顾问指引（真实项目里 AI 怎么用这些知识）

- **用户问"需求不清晰该用什么方法"** → 切克兰德软系统方法论（比较与探寻），区别于霍尔的硬系统（最优化）
- **用户讨论跨部门协作/前后端协同** → 关联并行工程（同时参与，避免串行返工）
- **用户讨论项目管理/技术方案好但推不动** → WSR 方法，提醒"人理"维度（关系、利益、协调）
- **用户讨论大型复杂系统/社会系统** → 关联综合集成法（开放的复杂巨系统）
- **用户做性能优化** → 必须先识别约束（找瓶颈）+ 指定负载 + 设目标；用阿姆达尔定律量化预期收益
- **用户想"换更快硬件能提升多少"** → 用阿姆达尔公式估算，强调"瓶颈决定天花板"
- **用户做容量规划/压测** → 关联 Web 服务器三大指标、基准测试程序分类
- **用户问该用哪种生命周期方法** → 按团队规模、需求清晰度、变更频率选（计划驱动/迭代/精益/敏捷）

## 三、常见误区（AI 自检红线，来自真实学习错题）

- ❌ **把系统工程等同于操作系统里的"系统"** → 系统工程是组织管理**方法论**，操作系统是具体**软件**
- ❌ **霍尔和切克兰德方法论混用** → 霍尔=**最优化**（硬系统，需求明确）；切克兰德=**比较与探寻**（软系统，需求不清晰）
- ❌ **并行工程说成"并行计算"** → 并行工程是**管理方法**（各部门同时参与生命周期），不是计算机的并行计算
- ❌ **WSR 把"人理"忽略** → 物理事理都搞定但项目推不动，往往就是**人理**（关系/利益/协调）的问题
- ❌ **阿姆达尔定律算错"增强比例"** → 增强比例是"可改进部分占**原总执行时间**的比例"，不是改进后的比例
- ❌ **以为"换快 N 倍硬件整体快 N 倍"** → 总加速比**永远小于**增强加速比，因为有不可加速的瓶颈
- ❌ **性能调整"瞎优化"** → 必须先**识别约束**（找瓶颈），不能凭感觉优化
- ❌ **混淆"指定负载"和"设置性能目标"** → 负载是输入压力（多大压力），目标是输出要求（达标标准），是一对，不是一回事
- ❌ **基准测试程序"测自己"** → 基准测试程序是测**硬件/系统**的（像考题考学生），不是测出题人
- ❌ **合成基准程序说成"最准确"** → 准确度排序：**真实程序 > 核心 > 小型 > 合成**，合成最不准（人工模拟难还原真实行为）
