## 一、核心知识体系

### 1. 访问控制 3 要素
| 要素 | 说明 | 性质 |
|------|------|------|
| **主体（Subject, S）** | 施加动作的实体（用户、用户组、终端、进程） | 主动 |
| **客体（Object, O）** | 接受访问的实体（文件、数据库、硬件、记录） | 被动 |
| **控制策略（KS）** | 主体对客体的访问规则集 | 规则 |

> 主体和客体角色**可互换**——当一个主体被其他实体访问时，它就变成客体。

### 2. 访问控制 3 方面
**认证 → 控制策略实现 → 审计**

- 认证：确认身份（你是谁）
- 控制策略实现：设定规则，保证合法用户的合法使用，防止越权
- 审计：记录操作行为，**防止管理员滥用**（管理员有赋权能力，无法用策略约束自己，只能靠审计兜底）

### 3. 访问控制 4 种实现技术
文件操作分 3 类：**R（Read 读）/ W（Write 写）/ O（Own 管理）**。

| 技术 | 存储方式 | 擅长查询 | 使用场景 |
|------|---------|---------|---------|
| 访问控制矩阵（ACM） | 整个矩阵（行=主体，列=客体） | — | 理论模型，大型系统矩阵巨大且空值多，实际不直接存 |
| **访问控制表（ACL）** | **按列（按客体）** | **谁有权访问这个客体** | **现代操作系统主流** |
| 能力表（Capabilities） | 按行（按主体） | 某主体能访问哪些客体 | 分布式系统 |
| 授权关系表 | 按非空元素（三元组） | 都可以（取决于排序） | 安全数据库系统 |

#### ACL vs 能力表（同一信息的两种视角）
- **ACL**：每个客体一张表，记录哪些主体可访问它。查"谁有权访问这个文件"方便（看这个文件的 ACL）；查"某用户对所有文件的权限"麻烦（要遍历所有 ACL）。
- **能力表**：每个主体一张表，记录它能访问哪些客体。查"某用户能做什么"方便；查"谁有权访问这个文件"麻烦。
- 现代操作系统（Linux、Windows 文件权限）主要用 ACL；授权关系表按主体排序等效能力表效率，按客体排序等效 ACL 效率。

> ACL 流行的原因：操作系统管理场景以客体（文件）为中心，"客体被访问时鉴权"是高频查询。

### 4. 数字签名的 3 个目的
1. **接收方能验证消息确实来自发送方**（身份验证）
2. **发送方不能否认发送过**（不可抵赖性）
3. **接收方不能编造或改变消息**（防篡改）

### 5. 数字签名的 5 个条件
签名可信 / 不可伪造 / 不可重用（不能移到别的文件） / 签名文件不可改变 / 签名不可抵赖。

> 传统手写签名不够的根因：计算机文件易复制、易剪切粘贴签名到别的文件、易修改不留痕迹。数字签名要解决的就是这些。

### 6. 数字签名的 2 种实现方式
| 方式 | 原理 | 缺点 |
|------|------|------|
| 对称密钥签名 | 需共同信赖的仲裁人 BB 作证 | 依赖仲裁人，不够去中心化 |
| **公开密钥签名** | 私钥签名，公钥验证（`D_A(P)` → `E_A(D_A(P))=P`） | 对长文件直接签名效率低 |

公钥签名的验证逻辑：
- 发送方否认 → 接收方拿出签名，用发送方公钥解密得到原文，证明是发送方发的（只有发送方有私钥）
- 接收方篡改 → 发送方要求出示原始签名，接收方拿不出来

### 7. 实际使用：数字签名 + Hash 函数（高频考点）
对长文件直接公钥签名效率太低，所以**只对文件的 Hash 值签名**：

```
发送方 A：
1. 计算 H = Hash(P)
2. 用 A 私钥对 H 签名：D_A(H)
3. 发送 [P, D_A(H)] 给 B

接收方 B：
1. 用 A 公钥解密签名得到 H：E_A(D_A(H)) = H
2. 自己算收到的 P 的 Hash 值 H' = Hash(P)
3. 比较 H 和 H'，一致则验证通过
```

**Hash 函数特性**：确定性数学运算（无随机数，同输入永远同输出）、固定长度输出、不可逆（压缩过程丢失信息，无法反推）。

**只签 Hash 值的好处**：
- 大大提高速度（公钥加密慢，Hash 把文件压成固定长度如 256 位，只签摘要快几个数量级）
- 签名和文件可分开存储
- 存储量降低
- 可验证文件存在而不需保存内容

> 工程经验锚点：Git 提交标识、文件完整性校验都是 Hash 应用，但要注意 Hash 是"压缩"不是"加密"。

### 8. 摘要 vs 签名的职责区分
- **消息摘要（Hash）** → 防篡改（文件改了 Hash 就变）
- **私钥签名** → 防抵赖（只有私钥持有者能签）

两者结合才完整实现数字签名的 3 个目的。

## 二、顾问指引（真实项目 AI 怎么用）

1. **权限模型选型**：操作系统/文件系统 → ACL；分布式系统常查"某用户能做什么"→ 能力表更合适；安全数据库 → 授权关系表。没有绝对最优，取决于场景。
2. **审计不可省**：管理员有赋权能力，策略约束不了管理员自己，必须有审计兜底。做权限系统别只做策略不做审计。
3. **签名 + 加密叠加**：要同时保密 + 防抵赖 → 先私钥签名再公钥加密（或反过来用对称密钥加密正文 + 非对称签名摘要）。
4. **长数据签名**：永远只签 Hash 值不签全文，效率差几个数量级。但要选密码学级 Hash（SHA-256 等），不要用 CRC 这类非抗碰撞 Hash。
5. **完整性校验**：文件分发/下载场景，给文件附 Hash 值让接收方校验，是低成本的防篡改手段。

## 三、常见误区（AI 自检红线，来自真实学习错题）

- ❌ **把 ACL 和能力表当两种不同信息** → 是同一信息的两种存储视角（按列 vs 按行），不是两种权限模型。
- ❌ **省略审计环节** → 访问控制 3 方面是认证 + 控制策略 + **审计**。审计专门防管理员滥用，因为管理员能赋权，策略约束不了他。
- ❌ **说"数字签名配合 Hash 只是为了方便"** → 太笼统。核心是**效率**：公钥加密慢，Hash 把文件压成固定长度只签摘要，速度快几个数量级；还能签名与文件分开存储。
- ❌ **把 Hash 当加密** → Hash 是单向压缩丢信息的运算，不可逆；加密是可逆的（有密钥就能解）。两者性质不同。
- ❌ **混淆摘要和签名的职责** → 摘要（Hash）防篡改，私钥签名防抵赖，两者各司其职，缺一不可。
- ❌ **主体客体当固定身份** → 角色可互换，主体被访问时就变成客体。
