## 一、核心知识体系

### 1. SOA 是什么（两个定义角度）

- **应用角度**：一个应用框架（业务灵活性 → 加快发展、降低 TCO、改善信息访问）
- **软件原理角度**：一个**组件模型**——功能单元（服务）通过良好定义的接口契约联系起来；接口中立，与**硬件平台、操作系统、编程语言三独立**。此角度对架构师更具指导性。
- 一句话定位：**服务 = 系统对外提供的功能集**；SOA 不仅是技术，**更是一个软件架构**——应用"拿来就用"、无需考虑底层集成，目标是 **IT 和业务同步**。

### 2. 演进脉络：为什么必须有 SOA（因果主线）

- **病：信息孤岛**。不同时期、不同工具建的存量系统互相调不通；且"从头重建不可能"（存量还在处理当前业务）。
- **前任的死因：EAI 两两翻译**。每个应用配中间件当"翻译"，N 个应用需要 N(N-1)/2 条翻译关系（5 应用 → 10 条，第 6 个加入新增 5 条）——平方级增长，死定了。
- **SOA 两步走破局**（顺序不能反）：① 把应用和资源**转换成服务** ② 把服务**变成标准的服务**形成共享。只做第一步 = **格式孤岛**（服务仍是各自格式，他人仍要专门适配——翻译题没消灭只换了层皮）。
- **总线解法**：点对点直连同样死于 C(N,2)（8 系统 28 条线）；上总线后每系统只接 1 条（星形 N 替代网状 N²）。
- **微服务 = SOA 的内部化**：SOA 服务化对象 = 企业已有**多个异构系统**（跨系统集成）；微服务把对象换成**单个应用内部**（单体拆小服务，去 ESB）。⚠️ ESB 是**连接件**不是对象。

### 3. 协议栈（Web 服务生态）

| 件 | 职责 | 记忆 |
|---|---|---|
| **SOAP**（Simple Object Access Protocol） | 消息传递通道，支持远程调用 | 信使/通道 |
| **WSDL**（Web Services Description Language） | 接口描述 | 说明书 |
| **UDDI**（Universal Discovery Description and Integration） | 注册+发现 | 黄页 |
| **BPEL**（Business Process Execution Language） | 服务编排，将分散服务组织成可执行复杂应用，产出复合服务 | 编排（是语言非协议） |

- 服务三角：提供者—发布(WSDL)→UDDI←—查找—请求者；**绑定调用（SOAP）直连提供者，运行时流量不过注册中心**。
- **QoS（WS-\* 规范族）**：三剑客不能满足关键任务系统的安全/可靠/事务需求 → 统称 QoS。五大类配对：可靠性→WS-Reliability/WS-ReliableMessaging；安全性→借助 **SAML**；策略→WS-Policy；控制→**BPEL4WS**；管理→**WSDM**。
- **REST**：设计风格而非架构。资源-URI 单向不对称（一资源可多 URI，一 URI 只对一资源）；**应用状态客户端维护 vs 资源状态服务端保存**（两状态易混）。REST 抛弃的是"机器替你操心的部分"（消息级安全/恰好一次/跨服务事务/强契约），有此类刚需（如银行转账恰好一次）时要自己补。

### 4. 参考架构六大类（给子服务归类用）

| 大类 | 管什么 | 钩子 |
|---|---|---|
| 业务逻辑服务 | 实现业务逻辑（已有/新/伙伴三组） | 干活的 |
| 控制服务 | 信息（联邦/复制/转换/搜索）、流程（编排/事务/人工）、交互（交付/体验/资源） | 粘合的 |
| 连接服务 | ESB | 运输的 |
| 业务创新和优化服务 | BPM 闭环、KPI 监控 | 看仪表盘的 |
| 开发服务 | 全生命周期开发平台 | 造东西的 |
| IT 服务管理 | 安全目录（SSO）+ 系统管理虚拟化 | 管家 |

- 信息服务判别：**本地有没有存数据副本**——联邦（数据不动，聚合查询）vs 复制（存副本，物化视图型）。
- 事务：**短流程两阶段提交 / 长流程补偿**（补偿 = 业务反向记账，≠ 回滚）。

### 5. ESB（本章第一高频考点）

- **正式定义四要素**：中间件技术实现的、支持 SOA 的基础软件平台；支持异构环境中的服务以**基于消息和事件驱动**模式交互；具有适当的**服务质量和可管理性**。
- **核心功能 6 条**：①位置透明的消息路由和寻址 ②服务注册和命名管理 ③多种消息传递范型（请求/响应、发布/订阅）④多种传输协议 ⑤多种数据格式及其相互转换 ⑥日志和监控。（⚠️ 容错/负载均衡/QoS 等高级能力不在 6 条清单内）
- **两个透明**：位置透明 + 协议透明。
- 中介转换**自动进行不需双方介入** → 请求者不关心提供者的位置和实现技术；双方接口不变、各自独立演变（= **消除了请求者与服务提供者之间的直接链接**）。
- 定性：ESB 是**架构模式，不能等同于特定技术或产品**；定位为理想的 EAI、B2B 集成支撑平台。
- 不同出处的功能清单版本不同（教材 6 条版 vs 真题 7 条版——后者多"消息增强/安全性"），答题先写两版共通内核：**位置透明路由 / 协议转换 / 格式转换 / 监控管理**。

### 6. SOA 八大设计原则（给描述选原则名）

①**无状态**（不依赖前次请求状态）②**单一实例**（避免功能冗余，DRY 的服务层版）③**明确定义的接口**（WSDL 定接口 + WS-Policy 规约 + XSD 定消息格式；稳定/明确/私有数据不可见）④**自包含和模块化**（独立部署/版本控制/自我管理/恢复 4 独立）⑤**粗粒度**（消息交互非 RPC、量大频度低——跨边界调用开销大，切太细开销放大）⑥**松耦合性**（位置/实现技术/当前状态三不可见）⑦**重用能力** ⑧**互操作兼容策略声明**（技术+业务语义皆用策略声明）。

### 7. 三个设计模式（套路）

- **服务注册表**：设计时段使用，控制点 = 策略执行点（PEP）；三大治理 = 服务注册（**限制谁能发布什么 = 最有效治理手段**）/ 服务位置 / 服务绑定。
- **ESB**：见上。
- **微服务**：5 优势（复杂应用解耦 / 独立开发部署+并行发布 / 技术选型灵活去中心化 / 容错故障隔离 / 松耦合易独立扩展）；**6 模式**（聚合器—调多个攒结果可再发布成组合服务；代理—**不聚合**只委派+转换；分支—两条独立链；链式—同步、链完成前调用方阻塞、**不宜过长**；数据共享—共享库表，单体→微服务**过渡权宜**；异步消息—消息队列替代 REST，加快响应，代价 = 可能降低可用性+增加复杂性）。链式与异步消息**共同敌人 = 同步阻塞**：链式接受同步限长度，异步换机制扔队列就走。**4 挑战**（分布式复杂性 / 分区数据库→弃强一致求最终一致 / 测试要启动全部依赖 / 部署监控分发扩容）。
- **SOA vs 微服务两个维度别串**：协调方式 = SOA 集中式（ESB 中介）vs 微服务去中心化；服务化对象 = 企业异构系统 vs 单个应用内部。

### 8. 构建 SOA 的检查单（动手前）

1. **四种集成需求全面排查**（≠ 全部实现）：应用程序集成 / 终端用户界面集成 / 流程集成 / 已有系统信息集成——简化或未明确定义 ≠ 没有。
2. **重用不替换遗留系统**：在现有投资基础上发展，整体替换成本极其高昂（孤岛既是病也是本金）。
3. **集成功能由服务提供，不由特定应用程序完成**——否则集成写死在应用里，那个应用一动全网跟着动（翻译账回来）。
4. **粒度外粗内细**：对外粗（挡住交互模式易变性），对内细（灵活复用）；细操作靠 **BPEL 组合成粗粒度服务接口**。粒度设计要害 = **编排责任归属**（后端做了操作但不能甩掉编排，否则退化成数据库的 HTTP 传声筒）。
5. **无状态设计**：Web 服务只能访问无状态 Session Bean；容器敢做负载均衡/群集的前提 = 无状态（任何实例能处理任何请求）。

### 9. SOA 实施流程（三步）

- **选方案**：全局规划（最基础一步）→ 考虑自身需求（进度和资金投入取决于 IT 应用沉淀 + SOA 目标层次）→ 平台考察（首选**开放性和对标准的支持**；实施 6 方面 = 业务战略和流程/基础架构/构建模块/项目和应用/成本和效益/规划和管理）。
- **建立服务模型（三法合用）**：
  - 自顶向下（领域分解）：从理想业务出发——业务组件模型 + 端到端流程分解到具备业务含义的最小单元 + 变化分析；**生产者**（发现主要候选者）。
  - 业务目标分析（目标服务建模）：KPI 前提，目标→子目标→服务 = 目标服务树，叶子可回溯目标；**审计器**（验证冗余/遗漏）。
  - 自底向上（遗留资产分析）：功能模块目录 → 发现**重复实现** → 包装成服务。
  - 中转：**服务是业务组件间的契约** → 划分到业务组件 → 层次化服务目录。
  - **变化分析 = 变化局部化**：易变逻辑剥离装盒，契约 = 盒与外界的分界面，变化只落盒内、外面不动；不剥离 = 波及效应。
- **建立业务流程（三小步）**：业务对象（实体=名词 / 过程=动词且依赖实体 / 事件，位于中间层）→ 服务接口（含多个语义相关操作；粒度双向判断——太细太粗都不恰当；**无状态接口最好**：理由①供很多使用者重用 ②各程序用最适合自己的方式管状态；特征句 = 请求消息包含完成操作的全部信息、不受调用顺序影响）→ 业务流程（活动顺序+明确输入输出提供业务值，异常必须捕获）。

## 二、顾问指引

- **集成选型判别句**：要转换**"数据"**的 → 信息集成（消息总线+协议及数据适配器）；要绕过**"内部逻辑"**借用现成界面的 → 界面集成；平台语言差异大的功能共享 → 服务化包装；动态定义协作关系 → 工作流引擎。数据格式的灵活转换实现 = **适配器模式**（统一转换接口类 → 各格式转换类继承实现）。
- **"为什么选 ESB"三方面论证**：部署 = 各应用只接总线一条线、即插即用；耦合 = 位置透明+协议转换、互不依赖；扩展 = 加服务不动存量。
- **粒度决策**：粒度随**单次跨边界调用成本**浮动（重信封中介 → 粗摊薄；轻量直连 → 细到业务能力级，底线 = 独立部署+独立数据库）。别教条"越细越好"。
- **什么时候不要微服务**：团队规模小 / 业务需求稳定 / 用户量不大 / 现有单体工作良好——迁移**不会有太多收益**，先付分布式复杂性+测试+部署三笔账。
- **分布式事务的取舍**：跨库两阶段提交"用不起"（锁全程不释放+网络拉长锁时间+协调者崩溃参与者无限期卡死）——本质**拿可用性换一致性**；长流程用补偿（业务反向记账），或接受最终一致性。
- **概念分层答客户问**：契约（业务约定，含策略）≥ 接口（技术声明，菜单）→ 服务（实现接口的可调用实体，厨房）。查找看接口（UDDI 存 WSDL），调用打服务实例（SOAP 绑定）。服务 vs SDK 的分界 = **进程边界+副本数**（SDK 各跑副本只消除重复编码；服务一份实现一实例一数据消除重复运行）。
- **组合 vs 集成**：看**产物**——组合 = 串成业务、产出新的粗粒度服务（BPEL 语境）；集成 = 连得上、产出连通性（EAI 语境）。集成是大圈，组合是小圈。

## 三、误区红线

1. **"SOA 是个技术方案，选它来集成"** ❌——SOA 是架构风格；集成方案落地选型打 **ESB**（部件），别拿整套风格答部件题。
2. **"微服务把 ESB 内部化了"** ❌——内部化的是**服务化对象**（企业异构系统 → 单个应用内部）；ESB 是连接件不是对象。
3. **"无状态 = 不受调用顺序影响"** ❌——那是**特征句**；两条**理由**是①多方重用②各程序自管状态。混用答一半丢一半。
4. **"有状态服务不能做"** ❌——是需要依赖时**定义成 BPEL 流程**把依赖收进流程内（服务间→服务内），不是禁止。
5. **"补偿 = 回滚"** ❌——补偿 = 业务反向记账（一正一反两个事务，痕迹保留）；回滚 = 抹掉一个未提交事务。
6. **"粒度细总比粗好 / 粗总比细好"** ❌——双向不恰当：太细病在外部易变性（请求者追着接口变），太粗病在复用单元太大/单体（要一部分得全要）。外粗内细各司其职。
7. **"EAI 的错在用了中间件"** ❌——错在**两两翻译的平方级拓扑**；ESB 也是中间件，换的是拓扑（星形 N）不是"要不要中间件"。
8. **"只上总线不做标准也行"** ❌——方言上总线：中介转换配置回到平方级，翻译搬进总线机房，EAI 换马甲回来。标准服务+总线缺一不可。
9. **"四种集成需求每个企业都要实现"** ❌——是**全面排查/考虑**，不是都要实现；简化 ≠ 没有。
10. **"服务是契约 = 功能扩大化"** ❌——是翻面（能力面→协作面）+ 筛选收缩（只公共边界部分进契约），内部功能不全部对外。
