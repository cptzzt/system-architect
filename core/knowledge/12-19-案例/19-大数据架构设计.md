## 一、核心知识体系

### 1. 章内主线

**传统单机方案为何失效（动机）→ 大数据系统的挑战与需求清单（8 属性）→ Lambda（批流合体三层）→ Kappa（纯流一套代码）→ 对比与选型（四维度四因素）→ 四个落地案例（选型验证 + 演进教训）**。

### 2. 传统方案的困境与演进链

异步队列（削峰，请求排队逐条落库，OLTP）→ 水平分区（固定切分，扩容要整体 reshard）→ 读写分离 Master-Slave + 分库分表（多副本一致性复杂度）→ Map/Reduce 批处理（整批算出查询视图，OLAP，实时性弱）——每一环都是"挤牙膏"式补丁。根因：**单机数据库对分区、复制与分布式查询不了解**；另一压垮主因=人为错误（传统系统无工程设计，仅靠备份不治本）。
- 辨析：异步队列治**峰值超载**（短时洪峰排队），治不了**持续超载**（水位线整体上移而已）；批处理与队列的本质差=逐条落库（OLTP）vs 整批算产视图（OLAP）。

### 3. 大数据系统的挑战与需求清单

- 三挑战：**85% 非结构化/半结构化数据**（结构化仅 15%）、复杂性不确定性难以刻画建模、**数据异构性 + 决策异构性**（桥梁=二次挖掘产出的"智能知识"）。
- 一次挖掘（海量原始数据→粗糙知识，机器）vs 二次挖掘（粗糙知识+量化主观知识→**智能知识**，人机结合）。
- **Marz 8 属性**（大数据系统需求清单）：鲁棒容错（**人为操作容错 > 机器容错**）/ 低延迟读写 / 横向扩容（scale out 非 scale up）/ 通用 / 延展 / 即席查询 / **最少维护（不能再基于传统架构的增量更新设计）** / 可调试——属性 7 是"不可变数据 + 全量重算"哲学的种子。

### 4. Lambda 架构（Marz 提出，批流合体）

- **三层**：**批处理层**（存主数据集 + 算 Batch View：全体数据、精确、重算、慢）｜**速度层**（最近增量、近似、增量更新、快、处理完即丢弃）｜**服务层**（合并两 View 低延迟对外 + 索引加速）。
- 批 vs 速两区别：**全体 vs 增量；重算 vs 增量更新**。三大原则：**不可变性 + 读写分离 + 复杂性隔离**。
- **主数据三属性**：原始的 / 不可变的 / 永远真实的。
- **最终精度（eventual accuracy）**：速度层的近似结果被下一组批处理视图**取代**——系统从"暂时近似"滑向"最终精确"。
- **容错哲学 = 源头完好 + 重算再生**：速度层算错→错误只在 Real-time View（衍生物），批处理按固定节奏全量重算覆盖后视图整体退役（"可过期的错误"·**无错误上报通道，不需要知道错了**·CAP 最终一致性的体现）；批处理层程序有 Bug→修算法后**从头重算视图**（主数据不可变故永远安全）。
- **Monoid（幺半群）**：满足**结合律**→计算可分解多机并行、部分结果可储存共享；**平均值不满足**→拆成分子/分母各自 Monoid 再相除；服务层合并三法=满足 Monoid 直接合并 / 拆多个 Monoid 函数 / 按业务规则。
- 分层三优点：容错（最终一致性）/ 复杂性隔离（增量算法的复杂圈在速度层，批处理层保持笨而稳=准确性压舱石）/ 横向扩容。
- 技术栈：**Kafka（总线）→ Spark/Storm（速度层）→ Hadoop HDFS + MapReduce（批）→ HBase/Cassandra（服务层·列族 NoSQL）+ Hive（可查询视图）**。
- 优 4（容错好/查询灵活[即席任何数据]/易伸缩/易扩展[加视图=加函数]）；缺 3（**两套编码开销 / 重新离线训练益处不大 / 重新部署迁移成本高**——全是 Kappa 登场的引子）。
- 血统：Event Sourcing（事件驱动/事件是核心要保存/业务数据只是事件产生的视图）；CQRS 属 DDD（读写分离因写拖累读）。

### 5. Kappa 架构（Jay Kreps 提出，纯流一套代码）

- **数据观**：数据系统 = 数据 + 查询；数据 = **When（产生于某时间点，日志隐含先后，数据库表 UPDATE 覆盖后丢失时间顺序）+ What（不可变的事实 Fact）**→ 操作只剩读和追加 = **CRUD 变成 CR**（Update/Delete 用追加记录，会计红字冲销式）。
- 结构：**删除 Batch Layer，数据通道以消息队列替代**；本质=改进 Lambda 的 Speed Layer，使其既能实时处理又能在业务逻辑更新时重新处理历史数据。
- **四步重放**（改算法后重算历史）：设保留期 Retention Period → 新作业实例 **Log Offset=0** 从头重放（结果写**新视图**）→ 新视图**追上**旧视图则切换读取 → 停旧实例删旧视图。全程**双跑不中断**（旧实例继续对线上，蓝绿部署思想）。
- 缺 3 条：**消息中间件性能瓶颈**（180 天级数据全存队列压力大）/ **多流关联易丢数据**（数据流先后顺序+算法逻辑）/ **抛弃了离线计算"稳"的一面**。
- 两个变形配对：**"存储归 Kappa+，展示归混合分析"**——Kappa+（流计算直接读 HDFS 数据仓库，配 Hudi）治消息队列瓶颈；混合分析（Kafka+Flink+ElasticSearch）治**展示层能力不足**（注意：不对应三条编号缺点），教材定性=Kappa 与 Lambda 间**折中**。
- 场景二分法：Kappa 擅长**增量写入/时序场景**（日志、点击流）；Lambda 擅长**历史探索性分析**。

### 6. 对比与选型

- 四维度：复杂度与成本（Kappa 赢，一套 vs 两套）/ 计算开销（Kappa 占优**但被排除出选型因素**——差别不大）/ **实时性打平**（两者都满足，不构成区分）/ 历史数据处理（Lambda 赢，批式全量吞吐大 vs 队列回溯制约）。
- 选型四因素：业务需求与技术要求（强制依赖 Hadoop/Spark/Storm→Lambda；偏好 Flink→Kappa）/ 复杂度（频繁改算法参数、想要一份代码→Kappa）/ 开发维护成本 / 历史数据处理能力（十年级海量历史→Lambda；始终小数据集→Kappa）。
- **"必须 Lambda"唯一明确反例：机器学习先离线批处理训练模型 → 模型是实时验证的前置输入 → 批流结果不能统一 → 两套省不掉**。

### 7. 案例套路（论文/案例通用）

- **答题四段骨架**：建设背景（业务+痛点）→ 数据需求与场景（N 大核心功能）→ 系统架构（分层 + 数据流分步）→ 应用效果（逐条回扣痛点）。
- **四案例选型映射**：奥运（秒级当日概览+海量赛事回顾）=Lambda｜广告平台（多来源指标、准实时+离线）=Lambda 三版演进｜证券日志（检索+指标+告警）=Kafka+Flink+ES+OpenTSDB=Kappa｜电商智能决策（实时流进模型、参数实时分发）=Kappa。
- **最有价值的实战教训**（广告平台演进）：数据来源多时标准 Lambda 会把**服务层塞成性能瓶颈**（查询时现场做关联聚合）；改进方向=**把服务层的工作不断提前到数据收集、计算层**（join 前移、关联前移到写入路径），终态服务层只读一张预聚合表。
- 常见落地链路：Kappa 参考架构 = 采集组件 → Kafka → Flink 统一引擎 → 检索库（原文）+ 时序库（指标）双库分工；参数/配置分发 = 服务端算好 → Zookeeper 通知 → 客户端拉取本地存储（查询路径零网络延迟）。

### 8. 数据湖与湖仓一体（教材外·论文真题高频落点）

> ⚠️ 此小节为"教材未讲、真题已考"的补充：近年论文题直考**数据湖 vs 数据仓库**多维对比、**湖仓一体四类关键特征**。

- **数据湖**：存储企业各种**原始数据**的大型仓库，任意规模三态数据（结构化/半结构化/非结构化）按**原有结构**集中存储，无须预先结构化处理。
- **湖 vs 仓对比（六维，以 Schema 时机为纲）**：数据来源（湖=三态全收 vs 仓=结构化）；**Schema 转换时机（湖=进湖不转、分析时才转=读时模式；仓=进仓前预定义=写时模式）**；存储成本（湖=非关系型低 vs 仓=关系型高）；数据质量（湖=原始未处理 vs 仓=清洗转换后"单一信息源"）；面对用户（湖=分析师+开发+数据科学家 vs 仓=分析师）；支撑应用（湖=机器学习/预测分析/数据发现 vs 仓=批处理报告/BI/可视化）。
- **湖仓一体（Lake House）**：湖缺事务一致性与实时处理、仓应付不了高并发多类型 → 融合。**四类关键特征（通行参考答案）**：①**事务支持（ACID）**②**模式实施与治理（Schema Enforcement，写时校验防脏数据）**——这两条=把仓库的本领搬进湖；③**BI 支持（直接在源数据上报表分析）**④**开放性（开放存储格式，一份数据多引擎访问）**——这两条=保住湖的红利。
- 出题趋势：2019 考"湖 vs 仓"对立，2022 考"湖+仓融合"——**新旧概念的辩证合题**，论文备好"对立→融合"叙事线。

## 二、顾问指引

- 用户说"数据量大，要不要上大数据架构"→ 先问三件事：**数据形态**（是否时序增量写入，如日志/点击流）、**历史分析需求**（是否海量任意条件探索分析）、**团队资源**（养得起两套系统吗）——再落 19.5 选型四因素。
- 选型一句话：**海量历史探索 / 强制依赖 Hadoop 系 / ML 先训后验 → Lambda；纯实时时序、频繁改算法参数、想要一份代码、小规模数据 → Kappa**。
- 别把"实时性"当选型依据——两种架构都满足实时性，真正的分水岭是**历史数据处理能力**和**复杂度/成本**。
- 现有 Lambda 系统性能瓶颈在服务层时，先查"服务层是否在查询路径上现场做关联聚合"——解法是把工作**前移到收集/计算层**，不是加机器。
- 写大数据类论文/方案：数据湖/湖仓一体是近年真题落点（教材未必覆盖），"湖 vs 仓六维对比（Schema 时机为纲）+ 湖仓一体四特征"是现成框架；案例用四段骨架 + 选型四因素论证。

## 三、误区红线

- ⚠️ **实时性维度打平**——不是 Kappa 实时更强，是两者都满足、不构成区分。
- ⚠️ **计算开销不作为选型考虑因素**——虽有差别但"相差不是很大"（教材原话口径）。
- ⚠️ Lambda 速度层的错误**不需要错误检测/上报机制**——错误不是被"纠正"而是被批处理重算**取代**（容器整体换掉）。
- ⚠️ **平均值不满足 Monoid**——不能把各部分平均值再平均，必须拆成分子/分母分别合并。
- ⚠️ 混合分析系统（+ElasticSearch）治的是**展示层能力不足**，**不对应** Kappa 三条编号缺点之一；Kappa+ 才治消息队列瓶颈。
- ⚠️ 数据湖 = **读时模式**（先存后解释），数据仓库 = **写时模式**（先定义后存）——方向说反则整道题崩。
- ⚠️ Kafka 是组件、Kappa 是架构模式——Kafka 是 Kappa 的典型实现底座之一，但 Lambda 里同样用 Kafka 当数据总线，两者不是绑定关系。
