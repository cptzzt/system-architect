## 一、核心知识体系

### 1. 软件工程为什么存在

- **软件危机**（20 世纪 60 年代提出）：早期软件靠个人手写、无文档、无系统方法，规模一大就出问题。
- 典型表现 6 类：进度难预测、成本难控制、功能难满足期望、质量难保证、难维护、缺文档。
- **软件工程 = 用工程化方法（系统化、规范化、可量化）解决软件危机**。

### 2. 软件工程过程的 4 个基本活动（PDCA 循环）

| 活动 | 含义 |
|------|------|
| **P 规格说明**（Plan） | 规定软件功能及运行限制 |
| **D 开发**（Do） | 产出满足规格的软件 |
| **C 确认**（Check） | 确认满足用户需求 |
| **A 演进**（Action） | 运行中持续改进以适应新需求 |

### 3. 五大过程模型（核心对比）

| 模型 | 核心特征 | 一句话定位 |
|------|---------|-----------|
| **瀑布** | 阶段严格串行，前阶段输出=后阶段输入，每阶段有里程碑审查 | 预设性、拒绝变化；需求必须先定死 |
| **原型** | 快速做一个能看的原型确认需求 | 边做边对齐认知 |
| **螺旋** | 每轮 4 步（目标设定→风险分析→开发验证→评审），**核心特征 = 风险分析** | 应对需求不明 + 风险高的项目 |
| **敏捷** | 适应性（拥抱变化）、面向人 | 短交付、迭代增量 |
| **RUP** | 用例驱动 + 体系结构为中心 + 迭代增量 | 重量级、过程完整 |

> **拥抱变化**：除瀑布外都算（原型/螺旋/敏捷/RUP）。
> **选型决策**：需求不明 → 原型；需求不明 + 风险高 → **螺旋**；需求明确 → 瀑布。

#### 原型模型的两种演化方向
- **抛弃型原型**：只为快速确认需求，确认后丢弃，用正规流程重做。
  - 为什么不直接用原型代码？**核心是质量不达标**（为赶工牺牲架构/规范/可维护性/性能），直接复用会累积技术债。**不是因为"用瀑布更快"。**
- **演化性原型**：在原型基础上不断补充完善，最终形成产品。

### 4. 敏捷方法

**两大特点**（vs 传统）：
- 适应性（adaptive，拥抱变化）vs 预设性（predictive，拒绝变化）
- 面向人（people-oriented，发挥创造力）vs 面向过程（process-oriented，人可替代）

**核心思想 3 点**：适应型而非预测型 / 以人为本而非以过程为本 / 迭代增量式开发。

**四种主要敏捷方法**：

| 方法 | 要点 |
|------|------|
| **XP（极限编程）** | 4 价值观：交流、朴素、反馈、勇气。朴素=从简单做起、不过度设计；勇气=实事求是地面对问题（重构、对不合理需求说不） |
| **Crystal 水晶系列** | 以人为本，提倡机动性，团队按项目选合适成员 |
| **Scrum** | 侧重项目管理。产品 Backlog → Sprint → Sprint Backlog → 可交付增量 |
| **FDD（特征驱动）** | 3 要素（人/过程/技术），6 角色，5 核心过程 |

> 注：XP 价值观用"实事求是"等通用表述，避免照搬教材特定措辞。

### 5. RUP（统一软件过程，重量级）

**二维模型**：
- 横轴（时间）：周期 → 阶段 → 迭代
- 纵轴（活动）：9 个核心工作流（业务建模/需求/分析设计/实现/测试/部署/配置变更管理/项目管理/环境）

**4 个阶段**（每阶段结束有里程碑评估）：

| 阶段 | 任务 | 里程碑 |
|------|------|--------|
| 初始 Inception | 定义产品视图和业务模型，确定范围 | 生命周期目标 |
| 细化 Elaboration | 设计确定体系结构，制订计划 | 生命周期架构 |
| 构造 Construction | 构造产品，演进需求/架构/计划 | 初始运行能力 |
| 移交 Transition | 提交给用户使用 | 产品发布 |

**4W 核心概念**：角色(Who) / 活动(How) / 制品(What) / 工作流(When)。

**三大特点**：
1. **用例驱动**：开发围绕"用户怎么使用系统"展开，用例贯穿需求/设计/实现/测试。
2. **以体系结构为中心**：架构是骨架，所有活动围绕它；用"4+1"视图描述。
3. **迭代与增量**：分多次迭代，每次只处理一部分需求。

#### "4+1" 视图模型（高频考点）

| 视图 | 关注者 | 关心什么 |
|------|--------|---------|
| 用例视图 | 分析人员、测试人员 | 系统行为（"+"那个 1，把其他视图串起来） |
| 逻辑视图 | 最终用户 | 系统功能 |
| 实现视图 | 程序员 | 配置、装配 |
| 进程视图 | 系统集成人员 | 性能、可伸缩性、吞吐率 |
| 部署视图 | 系统工程师 | 发布、安装、拓扑 |

### 6. CMM/CMMI 能力成熟度

- 由美国卡耐基梅隆大学 SEI（Software Engineering Institute）开发，用于过程改进和能力评估。
- 口诀：**初(1) 管(2) 定(3) 量(4) 优(5)**

| 级 | 名称 | 核心 |
|----|------|------|
| 1 | 初始级 | 混乱，靠英雄主义 |
| 2 | 已管理级 | 项目级有标准、有目标 |
| 3 | 已定义级 | 组织统一标准流程并制度化 |
| 4 | 量化管理级 | 建立定量目标，过程性能**可预测** |
| 5 | 优化级 | 持续改进，关注整体绩效 |

> **L3/L4 关键区别**：L3 有标准流程但**不保证结果**；"可预测性"是 L4 才有。
> CMMI 评估的是组织过程能力成熟度，是**概率性整体提升**，非具体项目交付绝对保证。

## 二、顾问指引（真实项目里 AI 怎么用）

用户问过程模型选型 / 项目该用什么开发方法时，按场景引导：

1. **需求明确且稳定**（如内部系统重写、合规系统）→ 瀑布/计划驱动更合适。
2. **需求模糊但风险可控**（如新产品 MVP）→ 原型/敏捷，先对齐认知再迭代。
3. **需求模糊 + 技术风险高**（如新领域、复杂集成）→ 螺旋模型，每轮专门做风险分析。
4. **大型企业级项目、需要完整过程资产** → RUP 思想（用例驱动 + 架构为中心 + 迭代增量）。
5. **用户问"我们公司过了 CMMI L3，项目能不能按时交付"** → 指出 L3 只保证"按统一流程做事"，不保证结果；可预测性是 L4 的事。
6. **用户分不清 RUP 4+1 视图** → 按关注者对应（用户看功能=逻辑视图、程序员看装配=实现视图、集成人员看性能=进程视图、系统工程师看拓扑=部署视图，用例视图是串联的"1"）。

## 三、常见误区（AI 自检红线）

- ❌ **螺旋模型的最大特点说成"迭代"** → 核心差异化特征是**风险分析**（每轮专门做风险识别和应对）。迭代是手段，风险分析才是它区别于其他模型的标志。
- ❌ **抛弃型原型不用是因为"瀑布更快"** → 核心是**质量不达标**（牺牲了架构/规范/可维护性）。原型只为确认需求服务，确认后使命结束。
- ❌ **CMMI L3 = 项目能按时交付** → L3 只保证"有制度化的统一流程"，不保证结果；"可预测性"是 L4。CMMI 是组织级概率提升，非项目级绝对保证。
- ❌ **XP"勇气"用 Kent Beck 原典说法纠正教材** → 考试/教材语境下以教材表述为准（朴素=从简单做起；勇气=勇于实事求是）。领域知识（原典的"敢于做正确但痛苦的事"）只能作为理解补充，且必须显式标注"教材之外"。
- ❌ **RUP "用例驱动"理解为"被使用的反馈驱动修改"** → 用例（Use Case）是描述"用户怎么使用系统"的分析工具；用例驱动 = 整个开发流程围绕用例展开（先写用例，再做设计/编码/测试）。
- ❌ **RUP "以体系结构为中心"理解为"抽象核心概念"** → 含义是架构是整个项目的骨架，所有开发活动围绕架构展开，用 4+1 视图从多角度描述。
- ❌ **把瀑布/原型/螺旋/RUP 当成互斥选择** → 实际项目常组合使用（如螺旋每轮内部可走瀑布步骤；RUP 是面向对象开发过程的代表，与 OO 方法同源）。
