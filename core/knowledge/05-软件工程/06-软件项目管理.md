## 一、核心知识体系

### 1. 项目管理概述（5.7.1）

- **70% 的项目失败因管理不善**（非技术原因）。软件是纯知识产品，进度和质量难估计度量。
- **4P**：人员（People）/ 产品（Product）/ 过程（Process）/ 项目（Project）。
- 目的：使项目按预定**成本、进度、质量**顺利完成。

### 2. 软件进度管理（5.7.2）

**6 个过程**：活动定义 → 活动排序 → 活动资源估计 → 活动历时估计 → 制定进度计划 → 进度控制。

#### WBS（Work Breakdown Structure，工作分解结构）

- 把项目层层分解，直到分解不下去为止。
- **分解链**：项目 → 任务 → 工作 → 日常活动。
- **工作包（Work Package）**：WBS 树形结构**最底层**，**最低层次的可交付成果**，应由**唯一主体**负责。
- **不超过 6 层**（过细 = 工作包失去意义 + 管理成本爆炸；不分解 = 无法落到责任人）。
- **5 要求**：工作包可控可管理 / 不过细（≤6 层）/ 每工作包有交付成果 / 每任务有完成标准 / 利于责任分配。

#### 任务活动图

- 活动定义 4 要素：**前驱 / 持续时间 / 必须完成日期 / 里程碑**。
- 展示工具：**甘特图（Gantt Chart）**（横轴日期、每行一任务、条形表时段）。

### 3. 软件配置管理 SCM（5.7.3）

**SCM（Software Configuration Management）**：标识、组织和控制修改的技术，应用于整个软件工程过程。
- 软件建立时**变更是不可避免的**。
- **目标**：标识变更、控制变更、确保变更正确实现、向其他人员报告变更。

**核心 2 项**：

| 内容 | 说明 |
|------|------|
| **版本控制** | 追踪文件变更（谁/何时/改啥，版本号+1）+ 并行开发（分支与合并） |
| **变更控制** | **目的不是阻止变更，而是管理变更、确保有序** |

**变更 2 来源**：
- **外部变更**（客户修改工作范围和需求）→ **最难处理**（控制权：客户说了算；时机：后期提出返工代价大）。
- **内部变更**（解决测试发现的错误而改源码/设计）。

### 4. 软件质量管理（5.7.4）

#### 软件质量定义
软件与**明确地和隐含地定义的需求**相一致的程度。

#### 影响质量的 3 组因素（高频考点）

| 因素组 | 时机 = 角色 | 包含特性 |
|--------|------------|---------|
| **产品运行** | 运行使用时 = 使用者 | 正确性、健壮性、效率、完整性、可用性、风险（6） |
| **产品修改** | 修改维护时 = 维护者 | 可理解性、可维修性、灵活性、可测试性（4） |
| **产品转移** | 转移/复用时 = 部署复用方 | 可移植性、可再用性、互运行性（3） |

> 口诀：**运行 6、修改 4、转移 3**。
> ⚠️ **3 组 = 生命周期 3 时机 = 3 类角色，两者一致（不是对立）**。可移植性归转移，因为发生在"搬走/换环境"时机。

#### SQA（Software Quality Assurance，软件质量保证）

**4 特点**：
1. **事前预防**（着重缺陷预防而非检查）。
2. **尽早捕获**（刚引入缺陷就捕获，不让扩散）。
3. **作用于过程**（不是最终产品）。
4. **贯穿所有活动**（不集中于一点）。

**定位**：以**独立审查**方式，从**第三方角度**监控开发执行。
**3 任务**：SQA 审计与评审 / SQA 报告 / 处理不符合问题。

> **SQA vs 测试**：SQA = QA（面向**过程**、**预防**、第三方）；测试 = QC（面向**产品**、**检测**发现缺陷）。**QA 治过程、QC 查产品**，互补。
> ⚠️ 注意：5.3 OOD 的"控制类"Control ≠ 5.7 QC 的 Control（质量控制），同词不同义。

#### 软件质量认证（2 种）
- **ISO 9000**：ISO 1994 提出，**一组标准的统称**（不是一个标准）。软件企业常用 **ISO 9001:1994**（20 方面质量要求）。
- **CMM**：卡内基梅隆 SEI 1987 研制，过程标准和成熟度等级认证（见 5.1.5 节 CMMI）。

### 5. 软件风险管理（5.7.5）

- **目标 = 预防风险**。
- 流程：辨识风险 → 评估出现概率及影响 → 建立规划管理风险。

**3 大体系**：

| 体系 | 划分 | 特点 |
|------|------|------|
| **Boehm** | 风险估计（辨识/分析/排序）+ 风险控制（计划/处理/监督） | 偏理论 |
| **Charette** | 分析（辨识/估计/评价）+ 管理（计划/控制/监督） | 偏理论，与 Boehm 接近 |
| **CMU-SEI** | SRE / CRM（Continuous Risk Management）/ TRM，与 CMM 配合 | **基于实践、最全面**，并将**需求方**纳入风险管理 |

> 区分：Boehm 和 Charette 都偏理论（且接近）；CMU-SEI 基于实践、最全面，强调把需求方作为风险管理要素。

## 二、顾问指引（真实项目里 AI 怎么用）

### 进度管理
- **做项目计划先 WBS**：把项目拆到工作包层级（唯一责任人、可交付成果），但**不超过 6 层**——过细管理成本超过分解收益。
- **用甘特图可视化**：横轴日期、每行一任务、条形表时段，一眼看清进度和依赖。

### 配置管理
- **小团队落地**：Git（管代码变更）+ 轻量 Issue 工具（GitLab Issue/MR、禅道、Jira，管需求/缺陷变更）。关键是流程——"变更必提工单 + 评估影响 + 审批 + 留痕"，比微信改 Word 强一个量级。
- **变更控制心态**：承认变更必然，建有序通道（申请/评审/CCB 裁定/追溯），而非堵它。强行阻止只能在初期定死所有需求，不现实。
- **重点防外部需求变更**：客户后期提需求是项目延期主因，要在合同/基线里约定变更流程和代价分摊。

### 质量管理
- **质量左移**：SQA 思想要在过程早期介入（事前预防 > 事后检查）。缺陷是过程产生的，改过程 = 治本；只查产品 = 治标。预防成本远低于返工成本。
- **区分 QA 和 QC**：建团队时明确——QA（过程/预防/SQA）和 QC（产品/检测/测试）是互补的两个职能，不要混为一谈。
- **评估质量维度**：用 3 组因素做质量检查清单（运行时 6 项、修改时 4 项、转移时 3 项），别遗漏可移植性等"非运行"质量。

### 风险管理
- **建风险清单**：辨识风险 → 评估概率和影响 → 制定应对计划，定期 review。
- **选体系参考**：Boehm/Charette 偏理论框架；CMU-SEI 基于实践最全面，且强调把需求方纳入——实战项目可借鉴 CMU-SEI。

## 三、常见误区（AI 自检红线）

- ❌ **WBS 分解越细越好** → **不超过 6 层**是经验阈值。过细 = 工作包失去意义 + 管理成本超过分解收益（边际效益递减）。
- ❌ **变更控制 = 阻止变更** → 变更控制**承认变更必然**，建有序通道让它流过，而非堵它。强行阻止只能在初期定死所有需求，不现实。
- ❌ **内部变更比外部难处理** → **外部需求变更最难**（控制权：客户说了算，开发方无自主权；时机：后期提出返工代价大）。内部变更自己能控、中途发现影响可控。
- ❌ **质量 3 组 = 3 类角色且与时机对立** → 3 组 = **生命周期 3 时机 = 3 类角色，两者一致**（运行/使用者、修改/维护者、转移/部署复用方）。不是对立关系。
- ❌ **质量转移组 = 管理者视角** → 转移组对应**部署/复用方**，不是"管理者"。
- ❌ **可移植性归产品运行/修改** → 可移植性归**转移**（发生在"搬走/换环境"时机）。
- ❌ **SQA = 测试 / 事后检查** → SQA 是**事前预防、作用于过程**（不是产品）、独立第三方审查。QA 治过程、QC 查产品。
- ❌ **风险体系 Boehm 基于实践、CMU-SEI 偏理论** → 反了：**Boehm、Charette 偏理论**；**CMU-SEI 基于实践、最全面**，且纳入需求方。
- ❌ **混淆"控制"一词** → 5.3 OOD 的"控制类"Control（控制业务流程）≠ 5.7 QC 的 Control（质量控制），同词不同义。
