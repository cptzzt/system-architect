## 一、核心知识体系

### 0. 概述

- **系统分析**：把复杂对象分解为简单部分，找属性和关系 → 产出**系统需求规格说明书**。
- **系统设计**：根据分析结果完成构建 → **概要设计 + 详细设计**。

### 1. 结构化方法（SASD）vs 面向对象方法（OO）—— 最高频考点

| 维度 | 结构化（SASD） | 面向对象（OO） |
|------|---------------|---------------|
| 拆分线索 | 按**数据流/功能**拆成处理模块 | 按**对象/事物**拆成对象 |
| 数据与操作 | **分离**（程序 = 算法 + 数据结构，以算法为主） | **绑定**（封装成对象） |
| 核心准则 | 分解与抽象、模块独立性、信息隐蔽 | 封装、继承、多态 |
| 开发过程特征 | SA → SD → SP 串行 | 用例驱动、体系结构为中心、迭代渐增（与 RUP 同源） |

> **根本区别**：结构化 = 数据和操作**分离**（数据游离在外被多函数共享）；OO = 数据和操作**绑定**（封装进对象，数据只由自己的方法操作）。
> OO 封装解决的痛点：结构化里数据被一堆分散函数共同读写，数据变了要改所有用到它的函数，牵一发动全身。

### 2. 结构化分析（SA）

**手段**：数据流图（DFD）+ 数据字典 + 结构化语言/判定表/判定树。

#### DFD（数据流图）4 种基本元素

| 元素 | 含义 | 图示 |
|------|------|------|
| 数据流 | 描述数据流向 | 箭头 |
| 处理 | 对数据的加工转换 | 矩形框 |
| 数据存储 | 数据库/文件形式存储 | 流入流出用箭头 |
| 外部项 | 数据源/终点（提供者或使用者） | 圆角框/平行四边形 |

#### 数据字典 5 部分

数据项 / 数据结构 / 数据流 / 数据存储 / 处理过程。
> DFD 是"图"，数据字典是"说明书"，配合成完整需求模型。

### 3. 结构化设计（SD）—— 高内聚低耦合

#### 耦合 7 种（模块之间，**低→高，越低越好**）

非直接 → 数据 → 标记 → 控制 → 通信 → 公共 → 内容

| 类型 | 关键 |
|------|------|
| 非直接耦合 | 两模块无直接关系 |
| 数据耦合 | 传递简单数据 |
| 标记耦合 | 传递记录等复杂信息（数据结构） |
| 控制耦合 | 传递控制模块内部逻辑的信息 |
| 通信耦合 | 共用输入或输出需整合 |
| 公共耦合 | 访问同一公共数据环境（全局数据） |
| 内容耦合 | 直接访问另一模块内部数据/代码 |

#### 内聚 7 种（模块内部，**高→低，越高越好**）

功能 → 顺序 → 通信 → 过程 → 时间 → 逻辑 → 偶然

| 类型 | 关键 |
|------|------|
| 功能内聚 | 只完成单一功能，缺一不可（最好） |
| 顺序内聚 | 处理元素必须顺序执行 |
| 通信内聚 | 集中在一个数据结构区域 |
| 过程内聚 | 必须按特定次序执行 |
| 时间内聚 | 同一时间间隔内执行 |
| 逻辑内聚 | 逻辑上相关的一组任务 |
| 偶然内聚 | 没有关系或松散关系（最差） |

> **设计原则：高内聚、低耦合。**
> ⚠️ 真题数据修正：耦合/内聚的 7 种排序**作为单独考点极少**（11 年真题约 1 道）。理解方向（高内聚低耦合）即可，不必死背 7 种顺序。
> ⚠️ "高内聚低耦合"**不绝对**：内聚和耦合是两个独立维度（内聚衡量模块内部、耦合衡量模块之间）。高内聚只降低耦合的可能性，不保证。

#### 详细设计工具 3 类

| 类别 | 工具 |
|------|------|
| 图形 | 程序流程图（最广）、PAD 图、NS 图（盒图） |
| 表格 | 操作-条件表 |
| 语言 | 伪码、PDL（外层语法确定描述控制结构，内层不确定描述操作） |

> ⚠️ PAD 图是**详细设计图形工具**，**不是 UML 的图**（易混考点）。

### 4. 结构化编程（SP）

Dijkstra 1965 年最早提出。3 种控制结构（顺序/选择/循环），**一个入口一个出口**，自顶向下逐步求精。

### 5. 面向对象分析（OOA）

**OOA 模型 = 5 层 + 5 活动**：主题层/对象类层/结构层/属性层/服务层 ↔ 标识对象类/标识结构/定义主题/定义属性/定义服务。

**OOA 9 原则**：抽象（**数据抽象是 OOA 核心**）、封装、继承、分类、聚合、关联、消息通信、粒度控制、行为分析。

两种对象类结构：**分类结构**（一般与特殊）、**组装结构**（整体与部分）。

### 6. 面向对象设计（OOD）—— 类分 3 种（高频）

| 类型 | 特征 | 举例 |
|------|------|------|
| **实体类** | **一定有属性，不一定有操作**（存永久数据，对应数据库表名词） | 用户类、订单类 |
| **控制类** | **一定有方法，不一定有属性**（控制协调用例业务，用例执行时产生、完则消亡） | 身份验证器、订单处理器 |
| **边界类** | **可既有属性也有方法**（系统与外界交接：窗体/报表/接口） | 窗口、通信协议、外部系统接口 |

> 属性/方法的有无是**职责的投影**：实体存在理由是"存东西"故必有属性；控制存在理由是"做事情"故必有方法。

### 7. 面向对象编程（OOP）

**OOP = 对象 + 类 + 继承 + 多态 + 消息**，核心是类和对象。
**3 大特点**：封装（高内聚低耦合的基本单位）/ 继承（单/多继承；取代/包含/受限/特化）/ 多态（同一消息不同对象不同动作）。

### 8. 数据持久化与 ORM

- 对象在内存，永久保存需**对象持久化** → 引入**持久层**（解耦业务逻辑和数据逻辑）。
- 关系数据库最广泛，对象持久化到关系库需 **ORM（Object/Relation Mapping，对象/关系映射）**。

| 框架 | 特点 |
|------|------|
| Hibernate | 全自动 ORM，POJO 与表映射，自动生成执行 SQL |
| iBatis | 半自动，需手动编写 SQL，小巧灵活（注：MyBatis 是 iBatis 的后续版本/新名字） |
| JDO | SUN 制定的对象持久化语义标准 API，透明存储，可跨数据底层运行 |

### 9. E-R 图（概念结构设计，数据库设计阶段）

3 种成分：实体（**矩形**）/ 属性（**椭圆**）/ 联系（**菱形**）。

联系 3 种约束：**1:1**（学校↔校长）/ **1:N**（专业↔学生）/ **M:N**（学生↔课程）。
> 1:1 是 1:N 的特例，1:N 是 M:N 的特例。联系也可有属性（如学生"选修"课程的"成绩"）。

## 二、顾问指引（真实项目里 AI 怎么用）

用户做系统设计 / 问架构拆分 / 问类设计时：

1. **先判范式**：项目是按业务流程组织（结构化/数据流思路）还是按领域对象组织（OO 思路）？现代业务系统多用 OO/DDD。
2. **拆分原则**：高内聚低耦合。但提醒"不绝对"——内部单一职责高内聚，不代表对外依赖少（如订单模块高内聚但调用库存/支付/物流多个模块）。
3. **类的职责分离**：实体存数据、控制做业务、边界对外交互，不要全塞一类。Spring Boot 的 Controller（边界，对人/前端）→ Service（控制，业务流程）→ Mapper/Repository（边界，对数据库）→ Entity（实体，数据）本质就是 OOD 三类职责分离的工程落地。
4. **警惕"控制类=数据搬运工"误解**：控制类是**业务流程指挥者**（如身份验证器），不是"传输接收数据"。
5. **判归属看职责不看名字**：Spring 的 `@Controller` 是 MVC 的 C（接收请求分发），按 OOD 属**边界类**；`@Service` 才对应 OOD 控制类。MVC 的 Controller 和 OOD 的 Control Class 是两套分类法里的词，恰好英文同形。
6. **E-R 转 表**：M:N 必须独立建关联表（如 user-product 的订单/购物车表）。

## 三、常见误区（AI 自检红线）

- ❌ **结构化 = "单纯的模块化" / "把同功能的数据和操作绑在一起"** → 结构化的根本特点是**数据和操作分离**（程序=算法+数据结构，数据游离被多模块共享）。"绑定"是 OO 的特点，不是结构化。
- ❌ **高内聚必然低耦合** → 两者是**独立维度**（内聚衡量内部、耦合衡量外部）。高内聚只降低耦合可能性，不保证。反例：订单模块高内聚但对外调用库存/支付/物流多个模块（高耦合）。
- ❌ **OOD 控制类 = "数据搬运工/传输接收"** → 控制类是**业务流程指挥者**（如身份验证器），职责是协调用例业务逻辑。
- ❌ **Spring 的 Controller = OOD 控制类** → Spring Controller 是 MVC 的 C，按 OOD 属**边界类**；Service 才是 OOD 控制类。判归属看职责不看名字。
- ❌ **PAD 图是 UML 的图** → PAD 是**详细设计图形工具**，不是 UML。UML 系统知识在第 2 章（类图/用例图/部署图等才是 UML）。
- ❌ **把 Mapper/Repository 当实体类** → Mapper/Repository 是**边界类**（对象世界与关系数据库之间的翻译关口），自己不持有业务数据。区分关键看"存不存数据"。
- ❌ **耦合/内聚排序当必考点死背** → 真题数据修正：7 种排序单独成题极少。理解"高内聚低耦合"方向即可，不必花大力气背顺序。
