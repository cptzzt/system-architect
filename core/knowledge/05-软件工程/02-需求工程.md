## 一、核心知识体系

### 1. 软件需求的 3 个层次（高频考点）

| 层次 | 视角 | 回答什么 |
|------|------|---------|
| **业务需求** | 客户/组织（**出资方、决策者**） | 系统要为组织达成什么高层目标 |
| **用户需求** | 用户（**使用者**） | 用户要完成什么任务 |
| **功能需求** | 开发人员（**实现方**） | 必须实现什么功能 |

> 口诀：**客户出钱、用户使用、开发做**——三者往往是不同的人。
> 补充概念：
> - **特性（feature）** = 逻辑相关的功能需求集合。
> - **非功能需求** = 标准/规范/合约、性能、设计或实现约束、质量属性。
> - **约束（constraint）** = 设计约束 + 过程约束。

> ⚠️ 易混点：软件工程里的"客户"指**出资/委托开发的甲方**（决策者），不是最终使用者。客户=出钱的，用户=使用的，开发=做的。

### 2. 需求工程（RE）概述

- 20 世纪 80 年代中期形成软件工程子领域。
- 需求分析**贯穿整个生命周期**，不限于开发最初阶段。
- 范围：覆盖**体系结构设计之前**的各项开发活动。

### 3. 需求工程的 5 个阶段（核心考点）

| 阶段 | 核心任务 |
|------|---------|
| ① 需求获取 | 交流/观察/分析任务，捕获修订用户需求 |
| ② 需求分析 | 建立**概念模型**，抽象描述需求 |
| ③ 形成需求规格（文档化） | 生成文档：用户原始需求书（协约）+ 软件需求描述规约（开发指南） |
| ④ 需求确认与验证 | 确认完整性/正确性/一致性/可测试性/可行性 |
| ⑤ 需求管理 | 追踪管理 + 变更控制 + 版本控制 |

### 4. 需求基线（Baseline）= 开发与管理的衔接点

- 需求文档经评审批准 → 定义**需求基线**，是双方**约定（Agreement）**。
- **需求约定是需求开发和需求管理之间的桥梁。**
- 关系：需求开发"从无到有"做出需求 → 基线 → 需求管理"定稿后管控"变更。
- **基线前**变更相对自由；**基线后**变更必须走变更控制过程 + CCB 裁定。

### 5. 需求管理 4 项活动

变更控制 / 版本控制 / 需求跟踪 / 需求状态跟踪。

### 6. 需求获取

**6 步骤**：开发高层业务模型 → 定义项目范围和高层需求 → 识别用户角色和代表 → 获取具体需求 → 确定业务工作流 → 需求整理总结。

**6 方法**：

| 方法 | 特点 |
|------|------|
| 用户面谈 | 最常见、理解需求**最有效** |
| 需求专题讨论会 | 集中涉众达成共识 |
| 问卷调查 | 确认假设、收集统计倾向，适合面谈后协作 |
| 现场观察 | 直观了解业务执行过程 |
| 原型化方法 | 解决早期不确定性（尤人机界面、查询报表） |
| 头脑风暴法 | 新业务、高度不确定项目 |

### 7. 需求变更（5.2.2）

变更是**常态**（需求获取不完整、理解误差、业务变化），但**无控制的变更**会导致项目混乱。

**变更控制过程 3 步**：
1. **问题分析和变更描述**：分析变更提议有效性，产生更明确的提议。
2. **变更分析和成本计算**：影响分析 + 评估所有改动成本，决定是否执行。
3. **变更实现**：按影响范围执行——计划驱动模型回溯到需求分析重做；敏捷模型纳入下一次迭代。

> 变更控制不是给变更设障碍，而是**渠道和过滤器**，确保采纳最合适的变更、负面影响最小。

**CCB（Change Control Board，变更控制委员会）**：
- 项目所有者权益代表，**裁定接受哪些变更**。
- **是决策机构，不是作业机构**——通过评审决定能否变更，**不提出变更方案**。
- 核心是**权力制衡 / 利益回避**：站在全局多方立场权衡利弊（利：客户满意度、竞争优势；弊：增加成本、推迟交付、质量下降）。既当裁判又当运动员会失去中立性。
- 可能成员 9 类：产品/项目管理、开发、测试/质量保证、市场/客户代表、文档、技术支持、帮助桌面、配置管理。

### 8. 需求追踪（5.2.3）

目的：建立"需求－设计－编程－测试"之间的一致性。

**两种方式**：

| 方式 | 查什么 |
|------|--------|
| **正向跟踪** | 需求 → 后继成果，查**缺**（需求有没有落地） |
| **逆向跟踪** | 成果 → 需求出处，查**多余**（成果有没有出处） |

> 正向 + 逆向 = **双向跟踪**，靠**需求跟踪矩阵**维护。
> 逆向跟踪的实战意义：揪出**镀金/过度工程**（开发自作主张加需求里没有的功能）。
> 实现可跟踪的前提：**统一标识每一个需求**。

## 二、顾问指引（真实项目里 AI 怎么用）

用户做需求分析 / 问需求管理时，按此引导：

1. **先分清三类需求**：用户说的"我想要 X 功能"往往是**用户需求**（任务），要往下拆成**功能需求**（开发要实现什么），往上问**业务需求**（出资方的高层目标是什么）。
2. **识别客户 vs 用户**：出资方和最终使用者往往不是同一拨人，需求采集要分别覆盖。
3. **基线意识**：劝用户对核心需求尽早评审冻结形成基线，基线后的变更走变更控制流程，避免无序蔓延。
4. **变更管理落地**：小团队可用 Git + Issue 工具（如 GitLab Issue/MR、禅道、Jira）做轻量变更控制，关键是"变更必提工单 + 评估影响 + 审批 + 留痕"。教材的 CCB 是流程，工具是把它电子化。
5. **跟踪矩阵**：用需求跟踪矩阵把每条需求链到设计/代码/测试，**双向都要做**——只做正向会漏掉镀金代码。
6. **需求获取方法选型**：用户说不清要什么 → 原型化/现场观察；新业务无前例 → 头脑风暴；大规模统计 → 问卷；关键决策方分歧 → 专题讨论会。

## 三、常见误区（AI 自检红线）

- ❌ **业务需求 = "最终开发目的"或"使用者视角"** → 业务需求站在**客户/组织（出资方）**视角，是高层目标，不是最终使用者的任务。
- ❌ **需求开发和管理 = "相互平衡、动态调整"** → 两者管同一批需求，但管的是**生命周期的不同动作**：开发"从无到有"做出需求到基线，管理"定稿后管控"变更。关系是**前后衔接**，不是平衡。
- ❌ **CCB 是作业机构 / "决策角度会乱"** → CCB 是**决策机构**（裁定变更、不提方案），核心是**权力制衡**——既当裁判又当运动员会失去中立性。问题不是"乱"，是失去多方制衡和独立审查。
- ❌ **只做正向跟踪就算"跟踪完整"** → 完整跟踪 = **双向**（正向查缺 + 逆向查多余）。只做正向会漏掉镀金/over-engineering。
- ❌ **基线 = "平衡点"** → 基线是双方约定，是开发和管理的**衔接点/桥梁**，不是平衡。
- ❌ **变更控制 = 阻止变更** → 变更控制**承认变更必然**，建立有序通道（申请/评审/CCB/追溯）让它流过，而非堵它。强行阻止只能在初期定死所有需求，不现实。
