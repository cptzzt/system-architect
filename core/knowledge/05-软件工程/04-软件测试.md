## 一、核心知识体系

### 1. 测试的定义与目的

- **定义**：用人工或自动手段运行/测定软件，检验是否满足规定需求，或弄清预期与实际的差别。
- **关键认知**：测试**贯穿整个软件开发过程**，不只是开发完才做。测试不仅发现错误，还给开发人员提供信息做风险评估。
- **目的**：发现错误、验证满足技术要求、为质量模型提供依据。

### 2. 测试方法（5.4.1）—— 三种分类角度

#### 按程序执行状态：静态 ST / 动态 DT

| 方法 | 是否运行 | 做法 |
|------|---------|------|
| **静态测试（ST）** | 不运行 | 分析/检查源程序语句、结构、流程图；对需求/设计/源程序做结构分析找错 |
| **动态测试（DT）** | 运行 | 运行被测程序比较实际与预期。3 步：构造实例 → 执行 → 分析 |

#### 按是否了解内部结构：黑盒 / 白盒 / 灰盒（高频）

| 方法 | 视角 | 做法 |
|------|------|------|
| **黑盒** | 把程序当黑盒，**不看内部结构** | 按需求规格设计实例，测界面和功能 |
| **白盒** | **借助内部逻辑和信息** | 检查每条通路；从程序结构出发。常用：控制流/数据流/路径分析、程序变异 |
| **灰盒** | 介于中间 | 既看输出正确性也看内部逻辑，但不如白盒详细；靠象征性现象判断内部运行 |

> **灰盒的适用场景**：当"内部结果错但输出碰巧正确"时（输出有欺骗性），黑盒会漏 bug、白盒成本高，灰盒靠象征性现象判断内部，**比白盒高效、比黑盒适用性广**。

#### 白盒覆盖标准（弱→强）

**语句 < 判定 < 分支 < 路径**

| 标准 | 含义 |
|------|------|
| 语句覆盖 | 每条语句至少执行一次（最弱） |
| 判定覆盖 | 每个判定的每个可能结果至少执行一次 |
| 分支覆盖 | 每个分支至少执行一次 |
| 路径覆盖 | 所有可能路径都执行（最强） |

> 质量要求高的模块一般要满足路径覆盖。

#### 按执行方式：人工 MT / 自动化 AT

| 方法 | 做法 |
|------|------|
| 人工测试（MT） | 人工执行 |
| 自动化测试（AT） | 预设条件下自动运行并分析，人驱动转为机器执行 |

### 3. 测试阶段（5.4.2）—— 严格只有 3 段

> ⚠️ **测试阶段 = 单元测试 + 集成测试 + 系统测试（3 段）**。下面的性能测试、验收测试等都是**系统测试的子类**，不是和系统测试并列的阶段。教材把它们作为专题小节并列展开是"展开篇幅"，不改变归属。

| 阶段 | 测试对象 | 方法 |
|------|---------|------|
| **单元测试** | 模块 | 静态 + 黑盒 + 白盒（模块小能查内部通路） |
| **集成测试** | 模块间**接口** | 白盒 + 黑盒结合（接口在内部需白盒看，同时黑盒验证组装功能） |
| **系统测试** | 整体是否符合需求 | **黑盒**，必须由**独立测试小组**进行，含回归测试，**缺陷归零**结束 |

> **单元用白盒、系统用黑盒的原因 = 测试对象决定**：模块小能读懂内部逻辑、可逐条通路查；系统整体太大无法逐条查，关注对外行为更重要。

#### 系统测试的子类

**性能测试**（系统测试子类）：
- **负载测试（Load Testing）**：负载渐增，看性能指标**变化趋势**。
- **压力测试（Stress Testing）**：找**瓶颈/临界点/最大服务级别**（找极限）。
> 区分：负载看渐变过程（找趋势），压力找崩溃临界（找极限）。

**验收测试**（系统测试子类，最后一个阶段）：
- 用户视角，满足用户需求/合同。通过后可发布。
- 与系统测试区别：系统测试是开发过程中的工作；验收测试由**用户**开展。

**Alpha 测试 vs Beta 测试**：

| 测试 | 环境 | 执行者 |
|------|------|--------|
| **Alpha 测试** | **开发环境**（或模拟实际操作环境） | 用户进行 |
| **Beta 测试** | **实际环境** | 多个用户测试，反馈给开发者 |

> 核心区别 = **环境**（开发环境 vs 真实环境）。

**其他新型测试**：AB 测试 / Web 测试 / 链接测试（3 方面：链到目标/页面存在/无孤立页面）/ 表单测试。

## 二、顾问指引（真实项目里 AI 怎么用）

用户问测试策略 / 测试设计时：

1. **按阶段分层设计测试**：
   - 单元测试 → 白盒为主（开发者自己写，覆盖核心函数逻辑，CI/CD 跑）。
   - 集成测试 → 白盒+黑盒（验证模块间接口契约）。
   - 系统测试 → 黑盒为主（独立测试小组，按需求规格验证端到端功能）。
2. **覆盖标准选型**：核心/高风险模块建议路径覆盖；普通模块语句/判定覆盖即可。
3. **性能测试规划**：先负载测试摸清性能曲线（找渐变趋势），再压力测试找崩溃临界点，两者可结合进行。
4. **验收测试**：交付前安排 Alpha（受控环境用户试用）→ Beta（真实环境多用户）两轮，能发现开发环境遗漏的问题。
5. **测试无法证明无错**：管理用户预期——输入域无穷（如两整数输入组合无限）、路径域也难穷尽。测试是**降低出错概率**，不是消除错误。这就是为什么还有"软件可靠性"专门研究。
6. **回归测试意识**：系统测试阶段需求变更导致程序改动后，必须多轮回归测试，防止改一处坏一片。

## 三、常见误区（AI 自检红线）

- ❌ **验收测试/性能测试是和系统测试并列的独立阶段** → 测试阶段**严格只有 3 段**（单元/集成/系统）。验收、性能都是**系统测试的子类**。教材专题并列展开是"展开篇幅"，归属不变。
- ❌ **灰盒用于"结果没问题所以用灰盒"** → 灰盒的理由是：**内部错但输出碰巧正确**（输出有欺骗性），黑盒会漏 bug、白盒成本高，灰盒靠象征性现象判断内部 → 比白盒高效、比黑盒广。不是"结果没问题所以用灰盒"。
- ❌ **单元测试只能用白盒、系统测试只能用黑盒** → 单元测试实际是**先静态 + 黑盒提基本用例 + 白盒验证**（黑盒满足不了覆盖时白盒增补）；集成测试是**白盒+黑盒结合**；系统测试主要用黑盒。"主要用"不等于"只能用"。
- ❌ **测试能保证软件 100% 无错** → 输入域无穷、路径域也难穷尽，测试本质是**降低出错概率**非消除错误。
- ❌ **负载测试 = 压力测试** → 负载看**渐变趋势**（性能指标随负载怎么变），压力找**崩溃临界/最大服务级别**。
- ❌ **Alpha/Beta 区别说成"执行者不同"** → 核心区别是**环境**（Alpha=开发环境、Beta=实际环境），执行者都是用户。
