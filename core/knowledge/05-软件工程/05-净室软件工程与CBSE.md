## 一、核心知识体系

### A. 净室软件工程（CSE，5.5）

#### 1. 核心哲学（关键考点）

- **净室软件工程（Cleanroom Software Engineering，CSE）**：用数学与统计学理论，追求**零缺陷或接近零缺陷**。
- **根本不同**：不是"先做产品再消除缺陷"，而是"**规约和设计阶段就消除错误，第一次就写对**"。
- 流程：写代码增量 → 在测试前验证正确性 → 尽量不靠跑测试。
- **甚至提倡不做单元测试**，用正确性验证 + 统计质量控制代替。
> 类比：无菌手术室——一开始就无菌操作（设计阶段消错），不是做完再消毒（事后修 bug）。

#### 2. 理论基础（2 个）

| 理论 | 解决什么 |
|------|---------|
| **函数理论** | 程序规范问题（程序 = 定义域→值域的函数） |
| **抽样理论** | 使用情况无穷不能全测，用统计抽样覆盖 |

**函数理论 3 特性**：
- **完备性**：每个输入**都有**输出。
- **一致性**：每个输入**只有一个**输出（不能同输入时 A 时 B）。
- **正确性**：由完备性和一致性推理验证。

#### 3. 技术手段（4 种）

| 手段 | 要点 |
|------|------|
| 增量式开发 | 统计过程控制下，划分为小累积增量，受控迭代 |
| 盒子结构 | 3 层：**黑盒（行为）→ 状态盒（状态机）→ 明盒（过程）**，支持信息隐藏/实现分离 |
| **正确性验证** ⭐ | **CSE 核心**，用数学推理证明确认代码符合规范（而非测试） |
| 统计测试 + 软件认证 | 使用模型 → 产生测试用例（样本）→ 推断整体性能 |

#### 4. 局限（3 条）

1. **太理论化**：需数学知识，正确性验证困难耗时，工程师须加强训练，**成本高**。
2. **不做传统模块测试不现实**：编译器/操作系统 bug 可能导致未预期错误。
3. 脱胎传统软件工程，带其弊端。

> **根本局限**：数学证明保证"逻辑上对"，**不保证"运行环境没坑"**。这就是不做模块测试不现实的原因。

### B. 基于构件的软件工程（CBSE，5.6）

#### 1. 核心思想

- **CBSE（Component-Based Software Engineering）**：基于分布对象技术，通过可复用构件构造系统。
- 哲学：**"购买而非建造"**，焦点**从"实现"变成"集成"**。
- 构件来源：COTS（商用现成）构件 或 自行开发。
- **前提假设**：系统间存在**足够多的共性**，复用才值得。（不是"有完备的构件"——完备构件是前提成立后的产物）
- 目的：更快构造、减轻维护负担、降低费用。

#### 2. 构件和构件模型（5.6.1）

**构件 5 特征**：可组装性（接口交互）/ 可部署性（自包含、二进制、无须部署前编译）/ 文档化 / 独立性（需依赖则显式声明）/ 标准化。

**构件模型 3 主流**：Web Services / EJB（Sun）/ .NET（微软）。

**构件模型 3 要素**：接口 / 使用信息（全局唯一名字、元数据）/ 部署。

**构件模型 2 种通用服务**：平台服务（分布式通信互操作）/ 支持服务（共性如身份认证）。

**中间件 + 容器**：中间件实现共性服务；容器 = 支持服务实现 + 接口定义，构件部署其中。

#### 3. CBSE 过程（5.6.2）

**6 活动**：系统需求概览 → 识别候选构件 → 根据构件修改需求 → 体系结构设计 → 构件定制与适配 → 组装创建系统。

**与传统开发过程 4 点不同**：
1. **早期需完整需求**（增量式不需要）→ 才能尽可能多识别可复用构件。
2. 根据可利用构件**修改需求**（构件反向约束需求，甘愿牺牲 100% 满足换降成本快速交付，典型工程权衡）。
3. 体系结构设计后有**构件搜索/设计精化**。
4. 开发 = **集成组装**（含开发适配器、额外功能）。

> **体系结构设计阶段特别重要**：选构件模型 + 平台，**决定并限制可选构件范围**（单行道，选错代价大）。

#### 4. 构件组装（5.6.3）

**3 种组装方式**：

| 方式 | 关系 | 口诀 |
|------|------|------|
| **顺序组装** | A 输出 → B 输入 | 接力赛（流水线串联） |
| **层次组装** | A 调用 B 服务 | 雇佣关系（请求/提供接口匹配） |
| **叠加组装** | 并放合成新构件，互不调用 | 拼装（合并功能，对外新接口） |

**3 种接口不兼容**：

| 不兼容 | 表现 |
|--------|------|
| **参数不兼容** | 同名但参数类型/个数不同 |
| **操作不兼容** | 操作名不同（如 login vs authenticate） |
| **操作不完备** | 提供是请求的子集（一方根本没有某些操作） |

> 解法：写**适配器构件**（把一个接口转换成另一个，不改动原构件）。

## 二、顾问指引（真实项目里 AI 怎么用）

### 净室相关
- 净室是**理论完美、实战难推广**的方法论。真实项目几乎不会全套照搬，但它的思想可借鉴：
  - **重要模块用形式化验证/契约式设计**（如关键算法、金融计算）替代部分测试。
  - **质量左移**：在需求和设计阶段就做评审/验证，而不是等产品做完再测（与 SQA 思想一致）。
- 用户问"为什么净室管不到编译器/OS bug" → 解释数学证明假设理想环境，运行环境 bug 不在证明范围内。

### CBSE 相关
- **判断项目是否适合 CBSE**：是否有足够多共性（行业通用功能多 → 适合；高度独特 → 不适合，做构件比直接写更贵）。
- **现代 CBSE 落地**：微服务、Spring Boot 生态、npm/Maven 依赖、Docker 镜像、API 网关都是 CBSE"购买而非建造"思想的工程实践。
- **构件集成现实**：买来的构件接口很少 100% 匹配，常需写适配器（Adapter 模式）转换接口，这是 CBSE 开发的主要工作之一。
- **关于"二进制构件"**：jar 包是典型二进制交付单元（字节码，给 JVM 跨平台），但仍需 JVM 运行时翻译成机器码（给 CPU）。"二进制形式" ≠ 机器码，泛指"非源代码的已编码产物"。

## 三、常见误区（AI 自检红线）

### 净室
- ❌ **净室顺序是"先验证再开发"** → 净室是"**写代码（增量）的同时，在测试前验证正确性**"，写和验证紧密结合，验证在测试之前。不是"先数学证明再开始写代码"。
- ❌ **函数理论一致性 = "一个输出对应一个输入"** → 一致性 = **一个输入只能对应一个输出**（不能同输入时 A 时 B）。方向易记反。
- ❌ **抽样理论 = "抽象"** → 抽样理论解决"软件使用情况无穷，用统计抽样有限覆盖"，与"抽象"无关。
- ❌ **正确性验证 = 测试** → 正确性验证 = **数学推理证明代码逻辑对**（事前）；测试 = **跑程序找 bug**（事后）。净室用前者替代后者。
- ❌ **正确性验证能发现编译器/OS bug** → 数学证明假设理想环境，运行环境 bug 不在证明范围内。这正是净室"不做模块测试不现实"的原因。

### CBSE
- ❌ **CBSE 前提 = "有完备的构件"** → 前提是"**系统间存在足够多的共性**"（完备构件是前提成立后的产物）。独特项目 CBSE 不适用。
- ❌ **CBSE = "换构件"** → CBSE 是**基于现成构件组装**，不是"换构件"。
- ❌ **顺序组装 = 层次组装** → 顺序 = **数据流接力**（A 输出喂 B 输入，流水线串联）；层次 = **服务调用**（A 调用 B 提供的服务，请求/提供接口匹配）。判别看关系：前后衔接=顺序，调用服务=层次。
- ❌ **"二进制形式" = 机器码** → 二进制形式泛指"非源代码的已编码产物"，字节码、机器码都算。jar 里是字节码（给 JVM，跨平台），机器码给 CPU（不跨平台）。
- ❌ **CBSE 不允许改需求** → CBSE 允许**反向改需求迁就构件**（构件反向约束需求），区别于传统"需求驱动实现"，甘愿牺牲 100% 满足换降成本快速交付。
