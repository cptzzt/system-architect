## 一、核心知识体系

### 1. 什么是软件可靠性（定性 + 定量两层定义）

**定性定义**：软件产品在**规定的条件下、规定的时间区间内**完成**规定功能**的能力。

**定量定义（IEEE/GB 标准）**：在规定条件下、规定时间内，软件**不引起系统失效的概率**。该概率是系统输入和系统使用的函数，也是软件中**已存在缺陷**的函数。

> 关键：可靠性用"概率"描述，因为软件失效是随机事件（路径随机），而缺陷是固有、不损耗的内在特点。

**三要素**（缺一不可）：
| 要素 | 含义 |
|------|------|
| 规定的时间 | 默认指**运行时间**（含工作 + 挂起空闲），是随机变量 |
| 规定的条件 | 运行环境（硬件平台、OS、DBMS、中间件、输入数据格式、操作规程等） |
| 规定的功能 | 任务决定调用的子模块/路径不同，可靠性也随之不同 |

### 2. 软件 vs 硬件可靠性的 4 个根本差异

| 差异点 | 软件 | 硬件 |
|------|------|------|
| 复杂性 | 逻辑高度复杂 → **设计错误是失效主因** | 相对简单 |
| 物理退化 | **无**物理退化（正确软件任何时候都可靠） | 失效主因是物理退化 |
| 唯一性 | 软件是唯一的，复制不改变本身 | 任何两个硬件不可能绝对相同 |
| 版本更新 | 频繁（需求变更/缺陷修复），评估难度大 | 定型后一般不变 |

> 推论：概率方法在硬件领域成功、在软件领域不令人满意，根源就在这 4 点。

### 3. 定量指标（必记公式）

| 指标 | 全称 | 定义/公式 | 备注 |
|------|------|----------|------|
| 失效概率 F(t) | — | 到时刻 t 出现失效的概率 | F(0)=0，单调递增，F(+∞)=1 |
| 可靠度 R(t) | Reliability | R(t) = 1 − F(t) | R(0)=1，R(+∞)=0 |
| 失效强度 f(t) | Failure Intensity | 单位时间失效概率，f(t) = F′(t) | F(t) 的导数 |
| MTTF | Mean Time To Failure | 平均失效前时间 = ∫R(t)dt | 针对不可修复系统 |
| MTTR | Mean Time To Restoration | 平均恢复前时间（故障→修复完成） | 越短 = 易恢复性越好 |
| MTBF | Mean Time Between Failures | 平均故障间隔时间 | **MTBF = MTTF + MTTR** |

> MTBF 公式前提：可靠度服从**指数分布**（此时任意时刻到故障的期望时间都相等）。

**三种"规定时间"**：自然时间（日历时间）/ 运行时间（启动到退出）/ 执行时间（CPU 实际执行指令时间）。其中**执行时间**最准确，效果最好。

### 4. 可靠性目标与失效严重程度类

**失效严重程度类**：对用户具有相同程度影响的失效集合。两种常见分级标准：
- 按**成本影响**分级（额外运行成本、修复成本、业务机会损失）
- 按**系统能力影响**分级（关键数据丢失、系统崩溃、用户操作无效等）

**可靠性目标** = 客户对软件性能满意程度的期望，通常用**可靠度 / 故障强度 / MTTF** 描述。建立目标需在**可靠性、交付时间、成本**三者间平衡。

> 关联：目标不是单值，要按失效严重程度类分别设（如致命失效要求 99.9999%，次要失效 90% 即可）。

### 5. 可靠性建模基础（9.2）

**软件可靠性模型**：为预计/估算软件可靠性所建立的可靠性框图和数学模型。目的：将复杂系统可靠性逐级分解为简单系统可靠性，便于定量预计、分配、估算、评价。

**影响软件可靠性的 5 大技术因素**：
1. 运行剖面（环境）——同一软件不同环境可靠性不同
2. 软件规模——代码量
3. 软件内部结构——越复杂缺陷越多
4. 开发方法和开发环境——结构化方法比非结构化缺陷少
5. 软件的可靠性投入——设计/管理/测试/评价投入

**根本驱动力**：缺陷的**引入、发现、清除**三环节。
- 引入 ← 产品特性 + 开发过程特性
- 发现 ← 用户操作方式 + 运行剖面
- 清除 ← 失效发现修复活动 + 可靠性投入

**模型的 4 个组成部分**：模型假设 / 性能度量 / 参数估计方法 / 数据要求。

**3 个共同假设**（至今主宰该领域，未找到克服方法）：
| 假设 | 内容 |
|------|------|
| 代表性假设 | 测试用例选取代表实际运行剖面（甚至独立随机） |
| 独立性假设 | 软件失效独立发生，互不影响 |
| 相同性假设 | 所有失效后果等级相同（不区分严重等级） |

**好模型的 5 特性**：基于可靠假设 / 简单 / 计算有用度量 / 给出好的未来失效映射 / 可广泛应用。

**模型分类（教材列 10 类）**：种子法、失效率类、曲线拟合类、可靠性增长、程序结构分析、输入域分类、执行路径分析、非齐次泊松过程（NHPP）、马尔可夫过程、贝叶斯分析。

> 仅做识别用途，记不住具体模型名不重要，知道"模型众多、按不同维度分类"即可。

### 6. 软件可靠性设计（9.4）—— 本章重点

**核心论点**：测试只能有限改善可靠性，**保障可靠性最有效、最经济、最重要的手段是在设计阶段进行可靠性控制**。

**3 条设计原则**：
1. 可靠性设计是软件设计的一部分，须在总体设计框架中使用，不与其他原则冲突
2. 以提高/保障可靠性为最终目标（在满足质量要求前提下）
3. 排在功能度、用户需求、开发费用**之后**考虑，不能无限扩大化

**认可且有应用前景的 3 大技术**：

#### 6.1 容错设计（失效后果严重的场合）
| 方法 | 原理 | 要点 |
|------|------|------|
| 恢复块设计 | 选一组操作作为容错单元，含若干功能相同、设计差异的文本，一文本故障则替换备份 → "动态冗余" | 单元可以是模块/过程/子程序/程序段 |
| N 版本程序设计 | 多模块/版本对相同输入的结果做**多数表决**，防某一版本故障 | 两大前提：①需求说明完全精确（不相关前提）②设计全过程不相关（不同算法/语言/编译器/工具/方法/甚至教育背景） |
| 冗余设计 | 在完整系统外，设计不同路径/算法/实现方法的模块作备份 | 注意：相同两套软件互备无意义（同环境必同故障）；额外费用远低于重写一个版本（文档/测试/人力可复用） |

#### 6.2 检错技术（无须在线容错、不能用冗余、但可靠性要求高的部分）
- 特点：故障后及时发现并报警，**代价低于容错/冗余**，但**不能自动解决故障**，需人工干预
- 4 个设计要素：
  | 要素 | 说明 |
  |------|------|
  | 检测对象 | 检测点（放易出错/影响大处）+ 检测内容（代表性、易判断指标） |
  | 检测延时 | 故障到自检出的时间；过长需换对象/方式 |
  | 实现方式 | 判断返回结果超范围 / 计算运行时间超预期 / 置状态标志位 |
  | 处理方式 | 多为"查出→停止→报警"，也可不停止/部分停止（取决于是否需实时处理） |

#### 6.3 降低复杂度设计
- 软件复杂度分**模块复杂性**（内部数据流向 + 程序长度）和**结构复杂性**（模块间关联程度）
- 复杂性是产生缺陷的重要根源：复杂度超阈值 → 缺陷数急剧上升 → 可靠性急剧下降
- 思想：保证功能基础上，**简化结构、缩短代码、优化数据流向**

#### 6.4 系统配置技术（系统级容错，9.4.4）
| 技术 | 说明 | 3 种工作模式 |
|------|------|------------|
| 双机热备 | 两台服务器 + 共享磁盘阵列 + 双机软件；用"心跳"信号维持主从联系 | ①Active/Standby（主备）②双机互备（彼此互为备机）③双机双工（均活动，负载均衡+互备） |
| 服务器集群 | 多台独立服务器在网络中组成单一系统统一管理；故障时应用自动被其他节点接管 | — |

> 教材注：FTA（故障树分析）、FMEA（失效模式与效应分析）等硬件成熟技术搬到软件领域效果有限，因软硬性质差异大。

## 二、顾问指引（真实项目 AI 怎么用）

- 用户问"软件和硬件可靠性有什么不同"：用 4 点差异讲，重点突出"设计错误是软件失效主因、物理退化是硬件失效主因"
- 用户问"MTTF / MTTR / MTBF 关系"：画清楚 MTBF = MTTF + MTTR，强调公式前提是指数分布
- 用户问"怎么提高软件可靠性"：先讲"设计阶段控制最有效"的论点，再分容错/检错/降复杂度三条路，按场景选（失效后果严重→容错；不能冗余但要求高→检错；通用→降复杂度）
- 用户问"N 版本怎么保证不相关"：强调需求说明精确 + 设计全过程不相关（不同人/算法/语言/工具）
- 用户问"双机热备和集群区别"：双机热备是两台 + 共享磁盘阵列为容错方案；集群是多台独立服务器组成单一系统，故障自动接管
- 用户讨论 Docker/微服务高可用：可类比"双机双工模式 + 集群"作为系统配置技术的工程实现

## 三、常见误区（AI 自检红线）

- ❌ **MTBF = MTTF**：正确是 **MTBF = MTTF + MTTR**（MTBF 包含故障时间和检测维护时间）
- ❌ **N 版本程序 = 多个相同副本**：N 版本要求设计**差异**（不同算法/语言/人），相同副本表决无意义
- ❌ **冗余设计 = 复制两套相同软件**：相同软件在相同环境必同故障，必须用**不同路径/算法/实现方法**
- ❌ **认为可靠性靠测试保证**：测试只能有限改善，**设计阶段控制**才是最有效最经济最重要的手段
- ❌ **混淆 MTTF 和 MTBF**：MTTF 针对不可修复系统（失效前平均时间）；MTBF 是故障间隔（含修复）
- ❌ **规定时间默认理解为日历时间**：默认指**运行时间**（启动到退出，含挂起），最准确的是执行时间（CPU 时间）
- ❌ **以为"降低复杂度"只是少写代码**：还包含简化结构、优化数据流向，分模块复杂性和结构复杂性两方面
- ❌ **检错技术能自动恢复**：检错只能发现+报警，**不能自动解决故障**，必须人工干预
