## 一、核心知识体系

### 1. 软件可靠性管理（9.3）

**定义**：软件工程管理的一部分，以全面提高和保证软件可靠性为目标，以软件可靠性活动为主要对象，把现代管理理论用于软件生命周期中的可靠性保障活动。

**内容**：软件工程各阶段的可靠性活动的目标、计划、进度、任务和修正措施。

**全生命周期可靠性活动**（每阶段并非必须项，按项目裁剪）：

| 阶段 | 主要可靠性活动（要点） |
|------|---------------------|
| 需求分析 | 定可靠性目标 / 分析影响因素 / 定验收标准 / 定管理框架 / 定文档规范 / 定初步计划 / 定数据收集规范 |
| 概要设计 | 定度量 / 定验收方案 / 可靠性设计 / 收集数据 / 调整计划 / 明确后续计划 / 编文档 |
| 详细设计 | 可靠性设计 / 可靠性预测 / 调整计划 / 收集数据 / 明确后续计划 / 编文档 |
| 编码 | 可靠性测试（含单元测试）/ 排错 / 调整计划 / 收集数据 / 明确后续计划 / 编文档 |
| 测试 | 可靠性测试（含集成/系统测试）/ 排错 / 可靠性建模 / 可靠性评价 / 调整计划 / 收集数据 / 明确后续计划 / 编文档 |
| 实施 | 可靠性测试（含验收测试）/ 排错 / 收集数据 / 调整模型 / 可靠性评价 / 编文档 |

> 现状：可靠性管理目前**停留在定性描述水平**，难用量化指标管理。怎样用有限投入达到预期目标是长期课题。

### 2. 可靠性测试概述（9.5.1 / 9.1.5）

**广义的软件可靠性测试**：为最终评价软件系统可靠性而运用**建模、统计、试验、分析、评价**等一系列手段对软件实施的测试。包含完整过程（定目标→定运行剖面→设计用例→实施→分析→可靠性数据→模型→评价）。

**狭义的软件可靠性测试**（也叫"软件可靠性试验" Software Reliability Test）：为获取可靠性数据，按预先确定的测试用例，在软件预期使用环境中对软件实施的测试。**面向缺陷**，以用户将使用的方式测试，每次测试代表用户将完成的一组操作 = 最终产品使用的预演。

**可靠性测试的 3 个目的**：
1. 发现需求、设计、编码、测试、实施等各方面的缺陷
2. 为软件使用和维护提供可靠性数据
3. 确认软件是否达到可靠性的定量要求

> 关键区别：一般测试方法（划分测试、随机测试、覆盖测试等）是**面向错误**的，结果数据**不能直接用于可靠性评价**，须经分析处理。可靠性测试才能直接产出评价可用数据。

### 3. 定义运行剖面（9.5.2）

**建模方法**：用**马尔可夫链**为软件使用行为建模——将输入域编码为代表用户观点的状态集，弧连接状态表示转换，转换概率分配给每个弧，代表典型用户的激励。

**两种分层**：
| 分层类型 | 依据 |
|---------|------|
| 用户级分层 | 谁/什么能激励系统（不同类型用户如何使用） |
| 用法级分层 | 测试状态下系统能做什么（所有功能） |

**概率估计来源（按优先级）**：
1. **现有系统数据**（最佳）——系统原型、前一版本使用数据
2. 用户/专家提供的预期使用数据（次之）
3. 每个状态现有弧分配相同概率（**最差**，无数据时才用）

**关键原则**：
- 可靠性测试假设每个操作输入有相同错误概率 → 最频繁操作表现出最高故障率
- 但**不能贯穿全部操作集合**：如飞机飞行控制软件，起飞/降落占比小但故障比例大
- **边界、跃迁、关键功能**不能用简单运行剖面，应**构造专门运行剖面**，补充统计模型外的测试用例
- 一个产品可能需要**多个运行剖面**，关键操作通常单独定义

### 4. 可靠性测试用例设计（9.5.3）

**核心**：在运行域上定义剖面镜像运行域，用剖面驱动测试，使测试真实反映使用情况。运用统计方法为每个元素定量赋予**发生概率值**和**关键因子**，据此分配测试资源、挑选用例。

**优先级原则**：优先测试最重要/最频繁的功能，释放最高级别风险，尽早发现对可靠性影响最大的故障。

**典型测试用例 8 组成**：标识 / 被测对象 / 测试环境条件 / 测试输入 / 操作步骤 / 预期输出 / 判断标准 / 特殊需求。

**强化输入**（比正常输入更恶劣，但合理程度内）重点关注 5 类特殊情况：
| 序号 | 测试目的 |
|------|---------|
| 1 | 屏蔽用户操作错误（误操作提示/屏蔽） |
| 2 | 错误提示准确性 |
| 3 | 错误是否导致系统异常退出 |
| 4 | 数据可靠性（有效性检查、冗余过滤校验清洗） |
| 5 | 异常情况影响（硬件/网络/部分模块失效，受损是否有补救） |

### 5. 可靠性测试实施（9.5.4）

**前置检查**：需求与设计文档一致性、过程文档准确性完整性、交付程序和数据与支持环境符合性。

**关键约束**：
- 必须**受控测试**：每个测试用例用**相同软件版本**，新版本 = 新测试开始
- 不能纯粹可靠性测试时（合同/标准约束），最佳选择 = 先非统计测试（如覆盖测试），后可靠性测试；**非统计测试放后面会影响评估准确性**

**可测试性难点**：判断用例运行成功/失败。控制系统失效可客观定义；一般应用失效更主观；科学计算若只输出错误结果而非系统失效则难发现 → 可**分两阶段**：第一阶段少量用例对照规范仔细检查，第二阶段大量用例找失效现象（错误信息/断电/崩溃/死机）。

**可靠性数据 4 类**（可互相转化）：
1. 失效时间数据（累积经历时间）
2. 失效间隔时间数据
3. 分组时间内的失效数
4. 分组时间的累积失效数

**每个测试记录 4 必含**：测试时间 / 测试用例标识 / 所有测试结果含失效数据 / 测试人员。

**测试报告 6 内容**：软件产品标识 / 测试环境配置 / 测试依据 / 测试结果 / 测试问题 / 测试时间。

### 6. 软件可靠性评价（9.6）

**3 个方面**：①选择可靠性模型 ②收集可靠性数据 ③可靠性评估和预测。

**评价用途**：开发过程中估计当前可靠性以决定是否终止测试发布；预计达到目标所需时间工作量；最终产品结合验证测试确认与需求一致性。

#### 6.1 怎样选择可靠性模型（4 维度）

| 维度 | 含义 |
|------|------|
| 模型假设的适用性 | 假设要符合软件系统现状，或冲突因素可忽略；逐条分析每条假设 |
| 预测能力与质量 | 根据现在/历史数据预测将来可靠性的能力及准确度；优先选成熟、应用广的 |
| 输出值满足评价需求 | 能否输出关键指标：当前可靠度/平均无失效时间/故障密度/达到目标日期/达到目标成本 |
| 模型使用简便性 | ①数据易收集且不超预算 ②简单易懂 ③便于工具实现 |

> 现状：可供选择的可靠性模型**极其有限**，制约了可靠性测试开展。

#### 6.2 可靠性数据收集

**现状 5 大问题**：
1. 规范不统一，度量定义混乱（时间/缺陷/失效/模型结构含糊）
2. 收集连续性不能保证（长期过程，投入常被忽略）
3. 缺乏有效数据收集手段（除可靠性测试外工具缺乏）
4. 数据完整性不能保证（遗漏数据影响评价结果）
5. 数据质量和准确性不能保证（不完全排错/诊断 → 虚假成分；不准确数据产生的误差可能比模型预测误差**大一个数量级**）

**4 项可行措施**：
1. 及早确定采用的可靠性模型 → 确定要收集的数据 + 明确定义术语
2. 制订可实施性强的收集计划，指定专人负责，多角色参与
3. 重视可靠性测试产生的数据整理分析（模拟实际环境，实用价值高）
4. 充分利用数据库完成存储和统计分析

#### 6.3 评估和预测

**常见需回答的问题**：
1. 是否达到可靠性目标？是否达到使用/中止测试条件？
2. 如未达到，还要投入多少时间/人力/资金？
3. 运行若干时间经维护升级后，能否达到交付水平？

**重要原则**：高可靠性要求系统须大量测试。**没有失效发生 ≠ 可靠度 1.0**（除非完全测试，而完全测试几乎不可能）。无失效时可基于**二项式分布**做保守估计，或凭经验按无故障运行用例数在置信度水平上估计。

**模型外辅助分析方法**：
| 方法 | 内容 |
|------|------|
| 失效数据图形分析法 | ①累积失效个数图 ②单位时间段失效数图 ③失效间隔时间图 |
| 试探性数据分析（EDA, Exploratory Data Analysis） | 数字化分析图形，发现异常：①循环相关 ②短期失效数急剧上升 ③失效数集中时间段 |

> EDA 常可发现：排错引入新缺陷、数据收集质量问题、时间域错误定义等。

## 二、顾问指引（真实项目 AI 怎么用）

- 用户问"可靠性测试和普通测试区别"：普通测试面向错误，数据不能直接用于评价；可靠性测试面向缺陷、镜像实际使用，数据可直接评价
- 用户问"怎么定义运行剖面"：马尔可夫链建模 + 用户级/用法级分层，概率优先用现有系统数据
- 用户问"测试中没有失效怎么评估"：不能认为可靠度 1.0，用二项式分布做保守估计或按无故障用例数经验估计
- 用户问"数据收集怎么做"：及早定模型→定数据规范→专人负责→重视测试数据→用数据库；强调"数据误差可能比模型误差大一个数量级"
- 用户问"选模型怎么选"：4 维度——假设适用性、预测能力、输出满足需求、使用简便性
- 用户讨论 CI/CD 中的可靠性：关联"受控测试需相同软件版本"原则——每次构建应视为新测试开始
- 用户做电商/支付系统：用"按失效严重程度类分级设目标"思路，区分致命失效（如支付失败）和次要失效（如 UI 抖动）

## 三、常见误区（AI 自检红线）

- ❌ **把可靠性管理等同于测试阶段活动**：管理贯穿**全生命周期**（需求→概要→详细→编码→测试→实施），每阶段都有可靠性活动
- ❌ **普通测试数据可直接做可靠性评价**：错误。普通测试面向错误，数据须经分析处理；只有可靠性测试数据才能直接评价
- ❌ **无失效 = 可靠度 1.0**：除非完全测试（几乎不可能），否则不能下此结论；应用二项式分布做保守估计
- ❌ **运行剖面只定义一个**：边界/跃迁/关键功能应**单独构造专门运行剖面**，不能简单处理
- ❌ **可靠性测试用不同版本**：必须相同软件版本，新版本 = 新测试开始
- ❌ **非统计测试（覆盖测试）可随意穿插**：应在可靠性测试**之前**完成，之后做会影响评估准确性
- ❌ **数据准确性无关紧要**：不准确数据产生的误差可能比模型预测误差**大一个数量级**，数据质量极重要
- ❌ **可靠性管理已成熟可量化**：教材明确说目前**停留在定性描述水平**，量化管理仍是难题
- ❌ **选模型只看预测准确度**：要综合 4 维度（假设适用性/预测能力/输出满足需求/使用简便性），实际可用模型很有限
