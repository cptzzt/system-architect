## 一、核心知识体系

### 1. 为什么需要演化（演化的重要性）
软件架构不是一次设计定终身，而是随需求、技术、环境变化持续修改完善的过程。教材原话大意：架构是**演化来的，不是设计来的**。

演化重要性的 3 条理由：
- 架构是系统骨架，直接决定性能、可靠性、安全性、可维护性；演化保证这些质量属性朝预期方向走
- 架构是蓝图，基于架构的检测/修改成本相对较低，从架构层面观察和控制演化最合理
- 架构演化更好保证软件演化的一致性和正确性、降低演化成本（3 个原因：形式化可视化表示提升可构造性；架构设计信息帮助预判演化情况；组件耦合描述支持动态调整）

### 2. 演化与架构定义的关系（SA 三要素演化）
软件架构 = 组件（Components）+ 连接件（Connectors）+ 约束（Constraints）。演化就是这三要素的增/删/改。

| 要素 | 含义 | 演化表现 |
|------|------|---------|
| 组件 | 计算元素、数据存储、重要模块 | 模块增删改 → 引发交互消息增删改（**波及效应**） |
| 连接件 | 组件间交互关系 | 交互消息的增/删/改 |
| 约束 | 组件与连接件的拓扑关系和配置 | 知识库中仿真数据的增删改 |

**关键术语**：波及效应（ripple effect）— 演化会牵连两类变更元素：直接受影响的 + 被波及影响的。最终由"两类变更元素 + 不受影响元素"共同组成演化后的架构。

### 3. 面向对象架构演化操作（UML 顺序图视角，4 大类）

#### 3.1 对象演化（2 种）
| 操作 | 含义 | 触发场景 |
|------|------|---------|
| AO（AddObject） | 顺序图中加新对象 | 加新功能 / 把现有功能独立化提升灵活性 |
| DO（DeleteObject） | 删除现有对象 | 移除功能 / 合并对象降低复杂度 |

> 单独的对象演化若不伴随消息演化无意义（孤立的零交互对象对系统无影响）。

#### 3.2 消息演化（5 种，顺序图核心）
| 操作 | 含义 |
|------|------|
| AM（AddMessage） | 增一条新消息 |
| DM（DeleteMessage） | 删一条消息（AM 逆操作） |
| SMO（SwapMessageOrder） | 交换两条消息时间顺序 |
| OM（OverturnMessage） | 反转消息发送方与接收方 |
| CMM（ChangeMessageModule） | 改变消息发送/接收对象 |

**消息演化与约束的 3 类关系**：
1. 与当前约束无关（如多数 AM）→ 不影响正确性/时态属性
2. 与约束直接关联但不违背（如改后仍满足约束）→ 不影响
3. 与约束关联并违背（如删除的某消息恰是某约束内容）→ **不正确演化**

#### 3.3 复合片段演化（4 种，控制流描述）
产生分支的复合片段类型：ref、loop、break、alt、opt、par。

| 操作 | 含义 |
|------|------|
| AF（AddFragment） | 在消息上新增复合片段 |
| DF（DeleteFragment） | 删除现有复合片段（AF 逆操作） |
| FTC（FragmentTypeChange） | 改复合片段类型（≈ 删旧 + 加新） |
| FCC（FragmentConditionChange） | 改复合片段内部执行条件 |

#### 3.4 约束演化（2 种，无可视化、不存自动机）
| 操作 | 含义 |
|------|------|
| AC（AddConstraint） | 添加约束（需判断当前设计是否满足新约束） |
| DC（DeleteConstraint） | 移除约束（一般架构都满足演化后约束） |

> 约束修改 = 删除旧约束 + 添加新约束，不单列。

### 4. 演化方式分类（3 种典型分类法）

1. **按实现方式和实施粒度**：基于过程和函数的演化 / 面向对象的演化 / 基于组件的演化 / 基于架构的演化
2. **按研究方法（Barnes 等人 4 类）**：对演化的支持 / 版本和工程管理工具 / 架构变换形式方法 / 演化成本收益分析
3. **按是否处于运行时期**：**静态演化** vs **动态演化**（本章重点）

### 5. 软件架构演化时期（4 阶段，按演化发生时机）
| 时期 | 时机 | 特点 |
|------|------|------|
| 设计时演化 | 编译前的模型阶段 | 最早、最易 |
| 运行前演化 | 编译后、执行前 | 应用未执行可改，需系统支持增删组件机制 |
| 有限制运行时演化 | 系统设计预设约束条件下 | 进入"安全模式"才允许规定好的演化操作 |
| 运行时演化 | 运行中不能满足需求时 | **最难**，含增删组件、升级替换、改拓扑 |

### 6. 静态演化（系统停止运行期间修改更新）

**静态演化需求 2 方面**：① 设计时演化需求（保证实现与架构一致）；② 运行前演化需求（发布后环境变化需修改升级）。

**静态演化一般过程（5 步，循环迭代）**：
```
原系统 → 软件理解 → 需求变更分析 → 演化计划 → 系统重构 → 系统测试 → 更新后系统
                                                                          ↑        ↓
                                                                       循环迭代 ←—
```
对应 3 类维护方法：**更正性维护 / 适应性维护 / 完善性维护**。

**原子演化操作**：粒度最小的架构修改操作（逻辑语义上），非物理不可分割。每经过一次原子演化形成中间版本 Ai。不同质量属性对应不同的原子操作序列。

**与可维护性相关的 8 种原子操作**（基于组件图）：
| 操作 | 说明 |
|------|------|
| AMD / RMD | 增 / 删模块间依赖关系 |
| AMI / RMI | 增 / 删模块间接口 |
| AM / RM | 增 / 删模块 |
| SM / AGM | 拆分 / 聚合模块 |

**与可靠性相关的 11 种原子操作**（基于用例图、部署图、顺序图）：
| 操作 | 说明 |
|------|------|
| AMS / RMS | 顺序图增 / 删交互消息 |
| AO / RO | 增 / 删交互对象 |
| AF / RF / CF | 增 / 删 / 改消息片段 |
| AU / RU | 为参与者增 / 删可执行用例 |
| AA / RA | 增 / 删参与者 |

**静态演化实例：正交软件架构（Orthogonal Software Architecture）**
- 核心思想：功能分层 + 线索化，**同一层次组件不允许相互调用**
- 收益：每个变动仅影响一条线索（限制波及范围，便于分析管理）
- 演化 5 步：① 需求变动归类 → ② 制订演化计划 → ③ 修改/增删组件 → ④ 更新组件相互作用 → ⑤ 产生演化后架构

### 7. 动态演化（系统运行期间的演化，不停机）

**两类需求来源**：① 软件内部执行导致的体系结构改变（如服务器收到请求时创建新组件）；② 外部请求对软件的重配置（如 OS 运行中升级不重启）。

**适用场景**：长期运行且特殊使命的系统（航空航天、生命维持、金融、交通），停机维护费用高、风险大、安全性差。

#### 7.1 软件动态性 3 级（Cuesta 划分）
| 级别 | 含义 |
|------|------|
| ① 交互动态性 | 固定结构下数据动态交互 |
| ② 结构动态性 | 组件和连接件实例的增删（**研究和应用主流**） |
| ③ 架构动态性 | 架构基本构造可重定义（如定义新组件类型） |

> 教材观点：目前研究多支持 1、2 级；**Cuesta 认为只有第 3 级才是真正的动态架构**。

#### 7.2 动态演化 4 方面内容
- **属性改名**：运行中重定义非功能属性指标（如响应时间）
- **行为变化**：需求变化或服务质量调节（如换加密算法、HTTP→HTTPS、组件/连接件替换重配置）
- **拓扑结构改变**：增删组件、增删连接件、改关联关系
- **风格变化**：一般保持不变；若必须变，只能变成衍生风格（如两层 C/S → 三层 C/S 或 C/S+B/S 混合）

#### 7.3 动态演化两种实现技术
| 技术 | 全称 | 侧重点 | 归类 |
|------|------|--------|------|
| DSA | Dynamic Software Architecture | 运行时框架结构自身变化，修改自身架构 | **架构动态性** |
| DR | Dynamic Reconfiguration | 从组件/连接件配置入手，运行中增删组件连接件 | **结构动态性** |

#### 7.4 DSA 实现原理与流程
**基本原理**：使 DSA 在运行系统中以"有状态、有行为、可操作的实体"显式表示，并被整个运行环境共享，作为系统运行依据。运行时架构相关信息的改变可触发/驱动系统动态调整。

**系统必须提供的功能**：① 保存当前架构信息（拓扑、组件状态和数目）；② 监控管理机制（监视需求变化，分析能否演化、何时演化、演化范围，生成演化策略）；③ **保证演化操作原子性**（操作失败则整个操作集撤销，避免系统不稳定）。

**DSA 实施 4 步**：① 捕捉并分析需求变化 → ② 获取或生成演化策略 → ③ 选择并实施演化 → ④ 演化后评估与检测。

**DSA 描述语言 3 类（按描述视角）**：
| 语言 | 视角 | 特点 |
|------|------|------|
| π-ADL | 行为视角 | 基于进程代数（π演算）描述动态性行为，为移动系统建模设计 |
| Pilar | 反射视角 | 基于反射理论，元系统修改反映到基系统；通常 < 3 层反射模型；源于 MARMOL（描述风格，非特定项目模型） |
| LIME | 协调视角 | Linda 在移动环境的扩展，分离计算部分和协调部分 |

**DSA 演化工具 4 类**：① 反射机制（如 K-Component、PKUAS、SASM、Artemis-ARC）；② 基于组件操作；③ 基于 π演算（SAAM 等）；④ 外部演化管理器（如 ArchStudio，含 Argo/ArchShell/扩展向导三种变更源）。

**PKUAS 实例**：符合 Java EE 规范的组件运行平台，4 类实体：容器系统 / 公共服务 / 工具 / 微内核（符合 JMX 标准）。

#### 7.5 动态重配置（DR）
**主要修改场景**：简单任务实现修改、工作流实例任务增删、组合任务流程个体修改、任务输入来源增删及优先级、组合任务输出目标增删及优先级。

**4 种重配置模式**：
| 模式 | 应用 |
|------|------|
| 主从（Master-Slave） | 主组件划分子任务给从组件，合并响应；主操作 + 主重配置两个正交状态图 |
| 中央控制（Centralized Control） | 实时系统常用，中央控制器控多组件 |
| 客户端/服务器 | 客户端发同步消息，事务完成后可增删客户端/服务器组件 |
| 分布式控制 | 分布式应用，含环形（Ring）和顺序（Serial）子类 |

**动态重配置 4 个难点**：① 约束定义困难；② 性能约束难静态衡量，需运行时评估；③ 难以同时管理所有方面；④ 需同时保证**组件系统完整性**和**重配置策略正确安全性**。

### 8. 架构演化 18 条原则（含度量方案）

> 口诀分组记忆（成本/进度/风险 → 结构/演化 → 模块/重构/重用 → 技术/环境/标准 → 质量/需求）：

| 序 | 原则 | 度量方案核心 |
|----|------|------------|
| 1 | 演化成本控制（ECC） | CoE << CoRD（演化成本远小于重开发成本） |
| 2 | 进度可控 | 实际与预期完成时间差越小越好 |
| 3 | 风险可控 | 时间/经济/人力/技术风险均不存在 |
| 4 | 主体维持（AIG） | AIG = 主体规模变更量 / 主体规模，平稳为佳 |
| 5 | 系统总体结构优化 | 检查整体可靠性和性能指标 |
| 6 | 平滑演化（IWR） | IWR = 变更总量 / 项目规模，相邻版本更新率相对固定 |
| 7 | 目标一致 | 阶段实际达成与预期目标差越小越好 |
| 8 | 模块独立演化（修改局部化） | 检查模块修改是否局部（计算影响范围） |
| 9 | 影响可控 | 影响范围可预测 |
| 10 | 复杂性可控 | CC < 某阈值 |
| 11 | 有利于重构 | 检查系统复杂度（越复杂越难重构） |
| 12 | 有利于重用 | 检查内聚度和耦合度（高内聚低耦合易重用） |
| 13 | 设计原则遵从性 | RCP = 冲突设计原则集 / 总设计原则集，越小越好 |
| 14 | 适应新技术（TI） | TI = 1 − DDT（DDT = 依赖技术集 / 用到技术集） |
| 15 | 环境适应性 | 硬件/软件兼容性 |
| 16 | 标准依从性 | 人工判定，不违背质量标准 |
| 17 | 质量向好（QI） | 演化后质量 > 演化前质量 |
| 18 | 适应新需求 | RNR = 适应新需求集 / 实际新需求集，越小越好 |

### 9. 架构演化评估方法（按演化过程是否已知分两类）

#### 9.1 演化过程已知的评估（核心思路）
将架构演化拆为一系列**原子演化操作**，形成中间版本序列 A0 → A1 → A2 → ... → An。对每个中间版本度量得质量属性值 Qi，进而得度量结果序列 Q0, Q1, ..., Qn。相邻版本间计算架构质量属性距离 D(i−1, i)。

**评估流程**：拆解原子演化 → 度量每个中间版本 → 得质量属性序列 → 计算质量属性距离 → 综合评估。

**架构质量属性距离计算**：
- **可维护性距离 Dm(A,B)**：6 项子指标（CCN、FFC、CBO、RFC、TCC、LCC）形成六元组，求两个向量**归一化的笛卡儿距离**
- **可靠性距离 Dr(A,B)**：实数值，简化归一化笛卡儿距离 = √((a−b)/(a+b))²

**重要性质**：
- D(0,n) ≠ D(0,1) + D(1,2) + ...（**原子演化影响不具累加性**）
- 质量属性距离应针对**同一架构的不同演化版本**度量（两完全不同架构质量相近没意义）
- 可靠性与物理组织结构无必然因果（结构相似度低但可靠性度量值可能相等）

**评估价值 3 方面**：① 架构修改影响分析；② 监控演化过程（得质量属性随时间变化曲线）；③ 分析关键演化过程（找质量发生大改变的时刻，利于故障定位）。

#### 9.2 演化过程未知的评估
无法追踪每一步变化 → **只能根据演化前后度量结果逆向推测**发生了哪些改变。

流程：演化前后架构分别度量 → 比较得质量属性变化与距离 → **逆向推测**演化操作集合及位置/对象 → 分析每个演化操作对质量属性的影响 → 推测高层驱动原因（修复代码错误、提高性能、平台移植等）→ 判断这些演化是否符合预期。

### 10. 大型网站系统架构演化实例（10 阶段）

> 核心逻辑：每阶段解决上一阶段的瓶颈，但引入新瓶颈 → 持续演化。

| 阶段 | 名称 | 解决的瓶颈 | 关键技术/手段 |
|------|------|----------|------------|
| ① | 单体架构 | （起点）资源争用 | 一台服务器放应用+数据库+文件 |
| ② | 垂直架构 | 单服务器性能/存储不足 | 应用、数据库、文件 3 服务器分离 |
| ③ | 缓存改善性能 | 数据库访问压力 | 本地缓存 + 分布式远程缓存（二八定律：80% 访问集中在 20% 数据） |
| ④ | 服务集群改善并发 | 单应用服务器连接数瓶颈 | 负载均衡调度 + 应用服务器集群（**可伸缩性**） |
| ⑤ | 数据库读写分离 | 缓存不命中读+全部写仍压数据库 | 主从热备 + 主写从读，数据访问模块对应用透明 |
| ⑥ | 反向代理和 CDN 加速 | 不同地区网络延迟 | CDN（运营商机房就近）+ 反向代理（中心机房缓存） |
| ⑦ | 分布式文件/数据库系统 | 单库/单文件系统容量上限 | 分布式 DB / 分布式文件系统（**最后手段**，更常用的是业务分库） |
| ⑧ | NoSQL 和搜索引擎 | 复杂数据存储检索需求 | NoSQL + 搜索引擎 + 统一数据访问模块 |
| ⑨ | 业务拆分 | 业务场景复杂 | 分而治之，按产品线拆应用独立部署，超链接/消息队列/共享存储关联 |
| ⑩ | 分布式服务 | 应用全连数据库导致连接资源耗尽（连接数 ≈ 服务器数²） | 共用业务提取独立部署，应用只管 UI，分布式服务调共用业务 |

## 二、顾问指引（真实项目 AI 怎么用这些知识）

- **用户问"架构要不要演化/重写"**：用演化成本控制原则（CoE << CoRD）判断；演化成本接近重开发成本时，重写更合理
- **用户做单体→分布式演进**：按网站 10 阶段顺序引导，每阶段先问"现在瓶颈在哪"，再决定下一步技术手段（不要跳级上微服务）
- **用户问"何时用动态演化/不停机升级"**：判断是否长期运行+特殊使命（金融/交通/生命维持类），且停机代价不可接受；普通 CRUD 系统静态演化足够
- **用户问 DSA vs DR**：DSA 改架构本身（架构动态性），DR 改组件连接件配置（结构动态性）；需求是"换组件实例"用 DR，"改架构构造"用 DSA
- **用户架构改动评估**：演化过程已知用中间版本度量+质量属性距离；未知用前后度量逆向推测
- **用户说"模块改一处影响很多地方"**：违反模块独立演化原则和影响可控原则，建议查内聚度耦合度、考虑正交架构思路
- **高并发选型**：缓存（二八定律）→ 集群（可伸缩）→ 读写分离 → 分布式，按瓶颈顺序推进，不要一上来就分布式数据库

## 三、常见误区（AI 自检红线）

- ❌ **把动态演化等同于"运行时改配置"**：DR（动态重配置）只改配置；真正的架构动态性（DSA 第 3 级）允许架构基本构造重定义，比 DR 更深
- ❌ **认为 D(0,n) = 各相邻距离之和**：原子演化的质量属性影响**不具累加性**，必须直接用 Q0 和 Qn 算
- ❌ **跨架构比较质量属性距离**：质量属性距离只对**同一架构的不同演化版本**有意义；两个完全不同的软件质量值相近不代表结构相似
- ❌ **混淆 4 个演化时期**：设计时（编译前）< 运行前（编译后执行前）< 有限制运行时（安全模式）< 运行时（最难）
- ❌ **把可靠性说成与架构结构正相关**：教材明确——可靠性与物理组织结构（逻辑依赖、调用）**无必然因果**，只与运行时逻辑交互复杂度相关
- ❌ **静态演化和维护类型对不上**：静态演化对应**更正性、适应性、完善性** 3 类维护
- ❌ **Cuesta 3 级动态性等级搞混**：交互 < 结构 < 架构；目前研究主流是**结构动态性（第 2 级）**，第 3 级（架构动态性）才是 Cuesta 认定的"真正动态架构"
- ❌ **演化原则 18 条只记名字不记度量**：考频重点是带度量公式的（成本控制 CoE<<CoRD、平滑演化 IWR、设计原则遵从性 RCP、适应新技术 TI 等）
- ❌ **网站演化阶段跳级**：分布式数据库是"最后手段"，常规应优先业务分库；NoSQL/搜索引擎通常在分布式 DB 之后
